# Matís vs Контур.Толк — Architecture Research

Дата: 2026-10-07. Только исследование: код, Docker, Caddy, LiveKit, TURN Matís **не менялись**, ничего не коммитилось.

Метки уровня доказанности:
- **CONFIRMED** — прямо сказано в официальной документации Контура (developer.kontur.ru, kontur.ru) или LiveKit (docs.livekit.io).
- **OBSERVED** — измерено в моих двух тестовых сессиях во встрече школы (штатный `chrome://webrtc-internals`, без внедрения в страницу Толка) или видно в публичном бандле клиента.
- **INFERRED** — вывод из CONFIRMED + OBSERVED; может быть неверен.
- **UNKNOWN** — публичных данных нет или проверка была невозможна.

## 1. Executive Summary

1. **Медиаядро Толка — Jitsi Videobridge, а не полностью собственный SFU.** Уровень: OBSERVED + сторонний источник, официального заявления Контура нет. Доказательства: интервью команды Контура (журнал «Код», 2024) — «в качестве хаба для маршрутизации… используется Jitsi Videobridge»; официальная документация on-premise — на хосте ktalk-media проверяют `/xmpp-websocket`, RTP на порту 10000, параметры `ktalk_media_bridge_*`; в браузере — lib-jitsi-meet, data channel «JVB data channel» с протоколом Colibri. «Собственная разработка» относится к прикладному слою: ktalk-app на .NET/C#, MongoDB, Angular-клиент, Electron, MCU, Barrel, вебинары.
2. **ktalk-media — SFU-кластер с каскадом** (CONFIRMED + INFERRED). Официально: «Одна конференция может быть запущена на множестве серверов одного кластера», «Толк будет автоматически распределять конференции по кластерам исходя из загрузки», «при потере кластера или одного сервера внутри кластера Толк переведёт конференции на другие серверы». Механизм каскада в доках не назван; по совокупности это Jitsi Octo/relay (INFERRED).
3. **ktalk-mcu — отдельный CPU-контур рендеринга** для записи, трансляций и SIP (CONFIRMED). Он отделён от realtime-медиа и масштабируется репликами: 2–3 CPU на задание с видео, 0,5 CPU на аудиозвонок; при недоступности сервера задания размещаются на других; если загружены все — отказ в начале записи. В версии 1.8 запись переходит на «рекордеры» с хранилищем S3, а постобработкой занимается отдельный сервис Barrel с очередью в MongoDB (CONFIRMED).
4. **Масштаб Толка по официальным цифрам:** до 400 участников во встрече (CONFIRMED). Сервер ktalk-media: 8 ядер и 60 Мбит/с — «до 30 онлайн-участников»; 12 ядер и 260 Мбит/с — «до 150 участников любого количества конференций» (CONFIRMED). Отсюда около 1,7–2 Мбит/с канала media-сервера на участника (INFERRED).
5. **Адаптация видео Толка (OBSERVED, мои сессии):** VP9 SVC `L2T3_KEY` (AV1 предпочтителен для камеры); слой выбирается по размеру плитки (240×180 против 480×360); фоновая вкладка — ноль видео; 250 кбит/с → сначала падает разрешение; 80 кбит/с → `L1T3`, 10 fps; восстановление 12–18 с.
6. **LiveKit закрывает большинство механизмов Толка** (CONFIRMED по docs.livekit.io): распределённый режим через Redis, выбор узла по нагрузке и региону (`node_selector`, `sysload_limit`), draining при выводе узла, встроенный TURN с TLS на 443, adaptiveStream, dynacast, simulcast/SVC, egress как отдельные воркеры. **Принципиальный разрыв один:** в OSS LiveKit «комната должна помещаться на одном узле» (CONFIRMED), а у Толка одна конференция может занимать несколько серверов кластера. Для школы, где много уроков по 2–30 человек, это не ограничение.
7. **Самый большой инфраструктурный разрыв Matís — всё на одном 2-ядерном хосте** (CONFIRMED по коду и серверу): SFU, TURN, API, PostgreSQL, Redis, Caddy и запись. Отказ хоста или его сети — это одновременная остановка всех уроков; запись делит CPU с SFU (egress без `cpuset`, `cpus: 1.5`); резерва медиаплоскости нет.
8. **Второй разрыв — прикладной уровень на один процесс** (CONFIRMED по коду): события урока идут через процессный `EventEmitter`, доска (Hocuspocus) — без Redis-расширения. Масштабировать медиа это не мешает (LiveKit горизонтален отдельно), но второй экземпляр API нельзя поставить без Redis pub/sub.
9. **Что Matís уже делает на уровне Толка или лучше** (CONFIRMED по коду + OBSERVED): выбор слоя по видимости, dynacast, проактивный перевыбор сетевого пути (у Толка по коду клиента — только после отказа ICE), восстановление медиа и присутствия, Redis в конфиге LiveKit уже есть (переход в распределённый режим не требует смены стека).
10. **Рекомендация** — не менять стек, а разнести роли: (1) запись на отдельный воркер или хотя бы отдельное ядро, (2) TURN/TLS 443, (3) второй LiveKit-узел с тем же Redis и draining, (4) мониторинг Prometheus из LiveKit, (5) позже — Redis pub/sub для событий урока, чтобы масштабировать API.

## 4. Kontur.Talk Architecture

### ktalk-app
- CONFIRMED: сервер приложения с основными сервисами и БД; несколько хостов за балансировщиком; внешний MongoDB с replica set; S3 (MinIO) для файлов; Barrel на хостах app по умолчанию.
- CONFIRMED: регистрация media-серверов и MCU, кластеры, «Серверы MCU → Активный» — ведутся в ktalk-app (раздел «Управление → Серверы»). Значит, **выбор media-кластера и MCU делает ktalk-app** (INFERRED, по Jitsi — через Jicofo-подобный фокус).
- INFERRED: сигнализация конференции — XMPP через `/xmpp-websocket` на media-хосте; ktalk-app выдаёт клиенту адрес и конфигурацию (в статическом бандле конфигурации нет — OBSERVED, значит, приходит с сервера).
- UNKNOWN: состояние конференции (где хранится), алгоритм балансировки (по CPU, по участникам, по каналу).

### ktalk-media
- **SFU?** INFERRED, высокая уверенность: JVB — это SFU (пересылает потоки, не микширует); OBSERVED — у получателя отдельные потоки участников, слой меняется по размеру плитки без перекодирования; микширование вынесено в MCU (CONFIRMED). Вывод «ktalk-media — SFU» не противоречит ни одному источнику.
- Участников на сервер: CONFIRMED только конфигурации — 30 на 8 ядер/60 Мбит/с, 150 на 12 ядер/260 Мбит/с. Точного предела — UNKNOWN.
- Горизонтально: CONFIRMED (кластеры, много серверов в кластере, несколько кластеров).
- Распределение: CONFIRMED «по текущей загрузке»; критерий — UNKNOWN.
- Перегрузка: UNKNOWN (для MCU — отказ, для media не описано).
- Падение сервера: CONFIRMED «переведёт конференции на другие, менее нагруженные серверы кластера». Сохраняется ли непрерывность медиа — UNKNOWN; по клиентскому коду lib-jitsi-meet при отказе ICE после XMPP-ping и 2 с перезапускается Jingle-сессия с мостом (OBSERVED в бандле) → INFERRED: у участников короткий обрыв медиа и пересогласование, конференция продолжается.
- Миграция идущей конференции: см. выше — CONFIRMED «переведёт», механизм UNKNOWN.
- Протоколы: CONFIRMED UDP 10000 (RTP), HTTPS/WSS; OBSERVED — DTLS-SRTP, SCTP data channel, TURN UDP 34788 и TLS 443 (SaaS).

### ktalk-mcu
- CONFIRMED: только для записи, трансляции и SIP (микширование, «отрисовка видео конференции для целевой задачи»); самый CPU-ёмкий компонент; отделён от media (свои VM); масштабируется репликами независимо; в 1.8 запись переходит к «рекордерам» (детали — UNKNOWN).
- Транскодирование вебинаров — отдельный `ktalk-webinar-transcoder` (CONFIRMED).

### TURN
- SaaS, OBSERVED: 4 TURN-сервера в разных площадках, `turn:` UDP 34788 и `turns:` 443/TCP.
- On-prem, CONFIRMED: STUN/TURN — внешние, указываются в настройках «Media Server»; собственного TURN-компонента в составе нет. Без TURN медиа идёт напрямую на UDP 10000 media-сервера.

### WebRTC (OBSERVED)
1 PeerConnection (`max-bundle`), offer от сервера, пересогласование при входе участника, VP9/AV1 SVC, simulcast-кодировки объявлены, активна одна SVC-кодировка, `x-google-start-bitrate=2000`, NACK/PLI, srflx → host моста (RTT 50 мс в моём случае).

### Signaling
CONFIRMED: XMPP WebSocket на media-хосте. OBSERVED (бандл): Strophe, возобновление XEP-0198 с `previd`, задержка 1,5 с × номер попытки с джиттером, пауза при `offline`, keepalive 60 с, XMPP-ping 65 с перед решением «ICE failed».

### Топология (только подтверждённые связи)

## 5. Media Scaling

| Масштаб | Толк | Уровень |
|---|---|---|
| до 30 онлайн | 1 media 8 ядер / 60 Мбит/с, 1 запись | CONFIRMED |
| до 150 во всех встречах | 1 media 12 ядер / 260 Мбит/с, 3 записи | CONFIRMED |
| 300 / 400 | больше серверов в кластере; одна встреча до 400 | CONFIRMED (лимит), раскладка — UNKNOWN |
| узлов в кластере, кластеров в SaaS | — | UNKNOWN |

**Один большой урок (1 + 29 против 1 + 149).** INFERRED: нагрузка SFU растёт примерно как «публикаторы × подписчики», а SVC, ограничение слоёв по плиткам и lastN режут исходящий поток. У Толка 150 участников укладываются в один рекомендованный media-сервер; при большем числе конференция может растянуться на несколько серверов кластера (CONFIRMED). У LiveKit комната ограничена одним узлом (CONFIRMED), но по их бенчмарку 150 видеопубликаторов × 150 подписчиков — 85 % от 16 ядер (CONFIRMED). Урок 1 + 149, где камеры у учеников в основном выключены и у каждого видно ≤12 плиток, по порядку величины помещается на один узел LiveKit 8–16 ядер (INFERRED, нужен замер `lk load-test`).

**Много маленьких уроков (10 × 30 против 1 × 300).** Для обоих продуктов это более лёгкий и хорошо масштабируемый случай: каждая комната целиком на одном узле, узлы добавляются горизонтально. У Matís сейчас один узел: класс 30 = ~12 % ядра (OBSERVED), то есть 10 × 30 по CPU — около 1,2 ядра. Но канал и запись, скорее всего, упрутся раньше (INFERRED; канала хоста под 300 участников при ~1,5–2 Мбит/с на участника нужно ~0,5 Гбит/с).

## 6. Failover

| Событие | Толк | Matís сейчас |
|---|---|---|
| Падение media-сервера | CONFIRMED: конференции переводятся на другие серверы кластера; непрерывность — UNKNOWN; INFERRED: короткий обрыв и пересогласование | один узел LiveKit — все уроки стоят до восстановления; клиент `MediaRecovery` переподключается сам, когда узел вернётся |
| Перегрузка media | UNKNOWN | UNKNOWN (не тестировалось за пределами 40 участников) |
| Падение MCU | CONFIRMED: задания размещаются на другом сервере; при общей перегрузке — отказ в начале записи | egress — один экземпляр; при отказе запись теряется (INFERRED) |
| Падение TURN | SaaS: 4 TURN-сервера (OBSERVED) | один coturn на том же хосте |
| Разрыв сигнализации | OBSERVED (бандл): XEP-0198 resume, пауза в офлайне | LiveKit resume/full reconnect + WS урока с бэкоффом и немедленной попыткой по `online` (с 2026-10-07) |
| Потеря сети, смена IP | OBSERVED (бандл): ICE failed → ping → перезапуск сессии; проактивной смены пути нет | LiveKit + `useMediaPathRefresh` (через 20 с плохого качества — ICE restart) |
| Wi-Fi ↔ LTE | **UNKNOWN**: живой тест заблокирован классификатором безопасности Claude Code | проверено ранее для iPhone (`ddd909a`) |
| Длинный обрыв | UNKNOWN | проверено 5–60 с (`matis-client-network-resilience-2026-10-04`) |

**Главный вопрос: продолжает ли работу уже идущая конференция после отказа media-сервера?** У Толка официально — да, «переведёт конференции на другие серверы». Как именно (участники заново подключаются автоматически или с разрывом), публично не описано → UNKNOWN. У LiveKit OSS при падении узла комната на нём исчезает; клиенты при full reconnect заново входят, и при наличии других узлов комната создаётся на свободном (CONFIRMED: комната создаётся на узле по node selector; INFERRED: Matís-клиент это переживёт благодаря `MediaRecovery`, которая заново делает `/join` и получает токен).

## 7. Recording

- **Толк** (CONFIRMED): запись, трансляция и SIP — на отдельном MCU-контуре с независимыми репликами и расчётом 2–3 CPU на задание; хранение и обработка — Barrel с очередью; в 1.8 запись переходит к «рекордерам» с S3. Запись не делит CPU с SFU.
- **Matís** (CONFIRMED по конфигу): LiveKit Egress (`room_composite_cpu_cost: 3.0`) — отдельный compose-проект **на том же 2-ядерном хосте**, `cpus: 1.5` без `cpuset` → может занимать ядро 0, закреплённое за LiveKit и coturn.

**Нужно ли разнести?** Да. Правильная схема:

```
Browser ─► LiveKit SFU (узлы медиа) ─► Egress worker(s) (отдельный хост/VM, подписывается на комнату как участник)
                                            └─► файл → хранилище (StorageAdapter/S3) → app (webhook egress_ended)
```
LiveKit Egress уже так устроен (воркеры регистрируются через тот же Redis и берут задания по `cpu_cost`) — менять стек не нужно, нужен только отдельный хост и `redis`/`ws_url`/`api_key` в его конфиге. Промежуточный шаг на одном сервере: закрепить egress за ядром 1 (`cpuset: "1"`), чтобы запись никогда не отнимала ядро SFU.

```
Browser (React 19, livekit-client 2.22)
```

## 12. Architectural gaps

Ранжировано по результатам исследования:

1. **Нет резерва медиаплоскости, всё на одном хосте** (SFU, TURN, API, БД, запись). Самый большой разрыв: у Толка медиа, приложение и MCU — отдельные масштабируемые роли с переводом конференций.
2. **Запись на том же хосте и может отнимать ядро SFU.** У Толка запись — отдельный CPU-контур.
3. **Один TURN, TLS не на 443.**
4. **API и доска — один процесс** (`EventEmitter`, Hocuspocus без Redis). Ограничит рост только после медиа.
5. **Нет метрик медиасервера** (Prometheus LiveKit выключен) — нечем решать, когда добавлять узел.
6. **Нет нагрузочного профиля на 100–300** (замеры только до 40).

## 13. What Matís should adopt

- Разделение ролей: app-хост, медиа-узлы, воркеры записи (принцип Толка, реализация — средствами LiveKit).
- Выбор узла по нагрузке и draining (у LiveKit из коробки).
- Отдельные воркеры записи с расчётом CPU на задание (`cpu_cost` у Egress) и отказом при перегрузке вместо деградации урока.
- TURN/TLS 443 и минимум два TURN.
- Телеметрия здоровья: Prometheus LiveKit + существующая клиентская телеметрия (по аналогии с health API Толка: `freezeCount`, `videoDownscaleRatio`).
- Нагрузочное тестирование `lk load-test` профилем урока перед каждым шагом роста.

## 14. What Matís should NOT adopt

| Не переносить | Почему |
|---|---|
| Jitsi/XMPP/Jicofo | смена стека без выигрыша: LiveKit покрывает маршрутизацию, выбор узла, адаптацию; XMPP добавляет компонент и протокол |
| Каскад одной комнаты на несколько серверов | в OSS LiveKit нет; уроки 2–30 человек помещаются в один узел |
| MCU-микширование для realtime | урок не нуждается в микшировании; запись уже делает Egress |
| MongoDB, RabbitMQ, ClickHouse, отдельный вебинарный контур | стек Matís (PostgreSQL + Redis) достаточен; это решения под корпоративный SaaS с вебинарами на 10 000 |
| Kubernetes на текущем этапе | 1–3 узла проще вести через compose + Ansible-подобный скрипт; Толк для on-prem тоже использует Docker + Ansible, а не K8s (CONFIRMED) |
| SIP-шлюз, киоски, федерации | не нужны школе |
| AV1 по умолчанию | программное кодирование тяжело для телефонов учеников |

## 15. Proposed Matís architecture at 30 / 100 / 300 / 1000 concurrent participants

Цифры — INFERRED по замерам Matís (класс 31 ≈ 12 % ядра LiveKit) и бенчмарку LiveKit; перед каждым шагом нужен `lk load-test`.

**30 (Stage 1, сейчас, 1 сервер).** Оставить как есть, но: egress — `cpuset: "1"` (или запрет записи при высокой нагрузке); `prometheus_port` у LiveKit; TURN/TLS 443 (второй IP); бэкапы PG вне хоста.

**100 (Stage 2, 2–3 медиа-узла).**
```
app-хост:   Caddy, Node/Fastify (1 экз.), PostgreSQL, Redis (пароль, приватная сеть)
media-1,2:  livekit-server (тот же Redis, keys), node_selector sysload_limit 0.6–0.7, coturn или встроенный TURN с TLS на своём IP:443
egress-1:   livekit-egress (тот же Redis), cpu_cost по замеру
```
Клиент подключается к сигнализации через Caddy (балансировка на media-узлы; любой узел проксирует сигнализацию в узел комнаты — CONFIRMED). Обновления LiveKit — по одному узлу с draining, без остановки уроков.

**300 (Stage 3, 3–5 медиа-узлов).** Redis Sentinel/реплика (LiveKit и API зависят от Redis); PostgreSQL с потоковой репликой; 2+ egress; канал узлов ≥1 Гбит/с. Прикладной уровень: при одном экземпляре API — вертикально; если API становится узким местом — Redis pub/sub для `roomEvents` и Hocuspocus Redis-extension (или маршрутизация урока на «свой» экземпляр по `lessonId`).

**1000 (Stage 4, 5–10 медиа-узлов, production-кластер).** Несколько экземпляров API за Caddy (после перевода событий на Redis), выделенные хосты TURN (2+), отдельное S3-совместимое хранилище записей, мониторинг (Prometheus + Grafana + алерты по `sysload`, потерям и заморозкам), при выходе за один регион — `regionaware` selector и geo-DNS. Kubernetes по-прежнему не обязателен.
