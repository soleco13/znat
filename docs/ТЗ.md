# Техническое задание: видеоплатформа для онлайн-школы

**Версия:** 1.3 — монолит на одном сервере + правило допуска внешних сервисов
**Дата:** август 2026
**Команда:** 1 разработчик + Claude Code
**Заказчик:** одна онлайн-школа (все школьные предметы, 1-11 класс)
**Архитектура MVP:** монолит, один выделенный сервер, `docker compose up`
**Принцип независимости:** ничего платного и ничего на критическом пути урока — снаружи. Бесплатное и некритичное можно (§10.10)

---

## 0. Краткая оценка: насколько это сложно

Честный ответ: **проект реалистичный, но это не «сайт», а платформа. Соло — примерно 9–12 месяцев до полной версии, ~4 месяца до состояния «можно вести настоящие уроки».**

Сложность неравномерная. Разложу по модулям (шкала 1–10, где 10 = «нужна команда»):

| Модуль | Сложность | Соло + Claude Code | Комментарий |
|---|---|---|---|
| Видео/аудио через SFU | **4/10** | 3–4 недели | LiveKit закрывает 90% работы. Сложность не в коде, а в эксплуатации |
| Доска с рисованием + синхронизация | **6/10** | 4–5 недель | Excalidraw даёт редактор, но CRDT-синк, права и права доступа пишешь сам |
| Вставка фото/материалов на доску | **3/10** | входит в доску | Excalidraw умеет изображения нативно |
| Режим презентаций (PPTX без демо экрана) | **4/10** | 2–3 недели | LibreOffice → PDF → PNG/SVG. Проверенный путь |
| Запись урока | **3/10** | 1 неделя | LiveKit Egress, но +CPU и +хранилище |
| **Движок интерактивных заданий** | **8/10** | 6–8 недель | Это второй продукт внутри первого |
| **Редактор заданий для методистов** | **9/10** | 8–12 недель | Самый недооценённый модуль. UX-ад |
| Эксплуатация (WebRTC в проде, TURN, мониторинг) | **6/10** | постоянно | 15–25% времени после запуска. Монолит на одной машине снимает ~половину этой боли |

**Главный вывод:** видеозвонки — это НЕ самая сложная часть. Самое дорогое — конструктор заданий для методистов. Он выглядит как «формочки», а на деле это WYSIWYG-редактор с версионированием, превью, валидацией и импортом. Люди годами делают такие штуки.

**Второй вывод:** идея «взять куски опенсорса и замесить в единое целое» верна, но только в правильной форме. Об этом раздел 2.

**Третий вывод (решение по архитектуре MVP):** всё живёт на **одном выделенном сервере**, приложение — **монолит** (один процесс Node, обслуживающий REST + WebSocket + Yjs + фоновые задачи). Это правильный выбор, и не «пока не выросли», а по существу:

- соло-разработчик физически не может эксплуатировать распределённую систему, при этом ещё и писать её;
- отладка WebRTC и CRDT на одном хосте на порядок проще: все логи в одном месте, никакой сетевой латентности между сервисами, `docker compose logs -f`;
- нет распределённых транзакций, нет service discovery, нет очередей между сервисами ради очередей;
- деплой = `git pull && docker compose up -d --build`;
- один арендованный dedicated-сервер с безлимитным каналом дешевле облака в 20–50 раз именно на видеотрафике (расчёт в §10.2).

Монолит здесь — это **не «всё в одном контейнере»**. Это один контейнер приложения + несколько стандартных сервисов рядом (Postgres, Redis, LiveKit, конвертер) на одной машине под одним `docker-compose.yml`. Границы, по которым система когда-нибудь разъедется, заложены в код с первого дня (§10.6), но разъезжаться она будет только когда упрётся, а не «на всякий случай».

## 1. Продуктовые границы

### 1.1 Что делаем

- Веб-платформа для проведения онлайн-уроков (браузер, без установки).
- Групповые уроки (класс до 30 учеников) и индивидуальные.
- Единый холст урока: доска + слайды + материалы + задания в одном пространстве.
- Редактор учебных материалов для методистов.
- Роли: **администратор**, **методист**, **учитель**, **ученик**. Всё.

### 1.2 Что НЕ делаем (явно из scope)

- CRM, оплаты, воронки, расписание с уведомлениями родителям.
- Личные кабинеты ученика/родителя с успеваемостью.
- Мобильные приложения (только адаптивный веб + PWA).
- Мультитенантность (одна школа = один инстанс). Заложим в схему данных `school_id`, но UI на одну школу.
- Свой SFU, свой кодек, свой CRDT.

**Отдельное требование заказчика — независимость платформы.** Формулировка точная и она задаёт правило, а не лозунг:

> Всё, что **платное** или **сильно влияет на стабильность и архитектуру**, — только своё.
> Всё, что **бесплатно** и **не влияет на работу урока**, — можно брать снаружи.

То есть цель не «ноль внешних имён в стеке», а «ничто внешнее не может остановить урок и не может выставить счёт». Формальное правило допуска, разбор по каждому сервису и список неустранимого — в §10.10–10.13.

### 1.3 Целевые нагрузки

Две колонки: что должен выдержать MVP на одной машине и куда растём. Разница принципиальна — второй столбец **не является требованием к MVP** и не должен влиять на решения сегодня.

| Параметр | MVP (одна машина) | Цель через год |
|---|---|---|
| Одновременных уроков в пик | **8–12** | 30–40 |
| Одновременных пользователей в пик | **120–200** | 600–800 |
| Средний размер класса | 12–20 | 12–20 |
| Максимальный класс | 30 | 30 |
| Длительность урока | 40–90 мин | 40–90 мин |
| Уроков с записью одновременно | **0–1** (см. §10.4) | 10–15 |
| Хранение записей | 30 дней | 90 дней |

Если школа уже сейчас даёт больше 12 параллельных уроков — не отказывайся от монолита, а вынеси медиа на вторую машину (§10.6). Это единственная развилка, которую стоит проходить досрочно.

## 2. Ключевое архитектурное решение: как правильно «мешать» опенсорс

Это самая важная часть ТЗ. Есть три способа собрать проект из чужого кода, и два из них убивают проект.

### ❌ Способ 1: форкнуть готовую платформу (BigBlueButton, Jitsi Meet)

BigBlueButton — самая близкая к твоим требованиям система: групповое видео, доска, загрузка презентаций без демонстрации экрана, опросы, breakout-комнаты. Всё уже есть.

Проблема: BBB построен на связке NGINX + FreeSWITCH + Kurento + Redis + Node.js + React, а в 3.0 добавились Hasura и GraphQL вместо Mongo/Meteor. Это Java/Scala/Kotlin + Node + Erlang-подобная акторная модель. Соло-разработчик, который форкнет BBB, становится мейнтейнером BBB, а не автором своего продукта. Каждый апстрим-релиз — конфликт мержа.

Отдельно: BBB форкнул tldraw на версии 2.0.0-alpha.19 — последней под Apache 2.0 — и обязался сам поддерживать этот форк. То есть даже они платят техдолгом за чужой код.

**Вердикт:** форк BBB оправдан только если ты готов не писать свой продукт вообще, а просто перекрасить BBB. Если цель — свой продукт со своим движком заданий, форк — ловушка.

> **Но:** прежде чем писать код, разверни BBB на день и проведи 3 реальных урока. Это лучшее ТЗ, которое можно получить. Возможно, окажется, что BBB + плагины (в 3.0 есть система плагинов для расширения ядра) решает 80% задачи за 5% времени.

### ❌ Способ 2: развернуть 5 контейнеров и связать iframe'ами

Excalidraw в одном iframe, Jitsi в другом, H5P в третьем. Работает на демо, разваливается на проде: нет общего состояния, нет общих прав, нет единой авторизации, три разных дизайна, невозможно синхронизировать «учитель листает слайд → у всех листается».

### ✅ Способ 3 (принятый): одно приложение + библиотеки + изолированные сервисы

**Два типа заимствования:**

**A. Библиотеки — вкомпилированы в твоё приложение** (npm-пакеты, ты владеешь UI и состоянием):
- Excalidraw как React-компонент
- Yjs как движок синхронизации
- LiveKit Components как UI видео
- pdf.js как рендер слайдов
- Tiptap как редактор текста

**B. Сервисы — отдельные процессы с чётким API** (ты не трогаешь их код, только конфиг):
- LiveKit Server (SFU) — gRPC/REST + WebSocket
- LiveKit Egress (запись) — REST
- Файловое хранилище — за интерфейсом `StorageAdapter` (в MVP локальная ФС, позже SeaweedFS)
- LibreOffice-конвертер — свой тонкий HTTP-воркер вокруг `soffice --headless`
- PostgreSQL, Redis

**Железное правило:** любой чужой код, который ты форкнул и правишь — это долг. Держи форки на нуле. Если библиотеку нужно допилить — оборачивай, а не форкай.

### 2.1 Монолит: что это значит на практике

Всё, что ты пишешь сам, — **один процесс Node**. Не «API + сервис досок + сервис заданий», а один `apps/api`, внутри которого модули.

**Один процесс обслуживает:**
- REST API (Fastify)
- WebSocket-каналы приложения (задания, прогресс, управление уроком)
- Hocuspocus как **встроенный** WS-эндпоинт на том же порту (`server.listen()` не отдельный — Hocuspocus умеет монтироваться в существующий HTTP-сервер)
- Фоновые задачи BullMQ (кроме конвертации файлов — см. ниже)
- Раздачу собранного фронтенда (`@fastify/static`)

**Рядом на той же машине, но отдельными контейнерами:**

| Сервис | Почему не внутри монолита |
|---|---|
| PostgreSQL | это база, она всегда отдельно |
| Redis | нужен LiveKit'у и BullMQ, отдельный процесс по природе |
| LiveKit Server | чужой бинарник на Go, свой сетевой стек, свой UDP-диапазон |
| coturn | чужой демон, свои порты |
| **Converter** (LibreOffice + Poppler + ClamAV) | **три причины:** (1) парсинг недоверенных файлов — классический вектор RCE, его нужно изолировать; (2) LibreOffice раздувает образ на ~1,5 ГБ; (3) конвертация даёт всплески CPU, которые нельзя пускать в один cgroup с медиа |
| Caddy | TLS и терминирование, 20 МБ |

Итого 7 контейнеров, один `docker-compose.yml`, одна машина, один `git pull`.

**Что явно НЕ делаем в MVP:** Kubernetes, отдельный сервис аутентификации, gRPC между своими модулями, message bus для внутренних событий, отдельный фронтенд-сервер с SSR, service mesh, несколько инстансов чего угодно.

## 3. Стек и выбор компонентов

### 3.1 Основной стек

| Слой | Технология | Почему |
|---|---|---|
| Фронтенд | **React 19 + TypeScript + Vite** | Excalidraw и LiveKit Components — React. Vite, не Next.js: приложение полностью клиентское, SSR не нужен и мешает WebRTC |
| Стили | **Tailwind CSS** | Скорость соло-разработки |
| UI-кит | **shadcn/ui (Radix)** | MIT, копируешь компоненты в проект, полный контроль |
| Состояние | **Zustand** + Yjs | Zustand для локального UI, Yjs для всего, что синхронизируется |
| Бэкенд | **Node.js 22 + TypeScript + Fastify** | Один язык на весь стек = соло-разработчик не переключает контекст. Fastify быстрее Express, лучше типизирован и умеет монтировать WebSocket-эндпоинты в тот же HTTP-сервер — что и делает монолит монолитом |
| Обратный прокси / TLS | **Caddy 2** | Автоматический Let's Encrypt в 5 строк конфига. Nginx даёт больше контроля, но в MVP это не нужно |
| ORM | **Drizzle ORM** | Типобезопасно, SQL-first, лёгкие миграции. Prisma тоже ок |
| БД | **PostgreSQL 17** | JSONB для материалов заданий — снимает 80% схемной работы |
| Кеш/pub-sub | **Redis 7** | Нужен LiveKit'у в кластере, нужен тебе для presence и очередей |
| Очереди | **BullMQ** | Конвертация PPTX, обработка записей, отправка отчётов |
| Файлы | **Локальная ФС + `StorageAdapter`** | Слайды, картинки, записи лежат в `/data/assets` на NVMe. Интерфейс `StorageAdapter` с двумя реализациями (`LocalFS`, `S3`) — переезд на self-hosted SeaweedFS позже стоит один день. Отдельное хранилище в MVP — лишний контейнер и лишний бэкап |
| Медиа-сервер | **LiveKit Server** | См. 3.2 |
| Реалтайм-состояние | **Hocuspocus (Yjs)** | См. 3.4 |

### 3.2 Видео: LiveKit

**Выбор: LiveKit Server, self-hosted.**

Обоснование: LiveKit полностью открыт под Apache 2.0 — можно читать код SFU, хостить у себя без поминутной оплаты. Из пяти живых опенсорсных SFU (mediasoup, Janus, LiveKit, Jitsi Videobridge, Pion) LiveKit — единственный, который даёт полноценную real-time-платформу «из коробки», а не низкоуровневый движок, и это правильный выбор, когда ценность продукта в продукте, а не в медиастеке.

Что даёт из коробки: SFU-роутинг, simulcast, adaptive bitrate (TWCC и REMB адаптируют качество в реальном времени), демонстрация экрана, data channels, готовые React-компоненты, шифрование (DTLS-SRTP для медиа, TLS для сигналинга — не опция, а обязательное поведение).

Почему не альтернативы:
- **mediasoup** — гибче, но ты пишешь весь оркестратор сам. +2 месяца работы.
- **Jitsi Videobridge** — Apache 2.0, но Kotlin/Java стек и заточен под Jitsi Meet.
- **Janus** — C, плагинная модель, силён в SIP-интеропе, которого тебе не нужно.
- **Свой на Pion** — нет.

Компоненты LiveKit, которые берём:
- `livekit-server` — SFU
- `livekit-egress` — запись уроков
- `@livekit/components-react` + `livekit-client` — фронтенд (официальные React-компоненты, состояние и события обрабатываются за тебя)
- `livekit-server-sdk` (Node) — генерация JWT-токенов, серверные API, вебхуки
- **coturn** — TURN-сервер (обязателен: часть учеников за корпоративными/школьными NAT)

Референс для изучения: `livekit-examples/meet` — полнофункциональное приложение видеоконференций на LiveKit Components. Не форкать — читать и брать паттерны.

### 3.3 Доска: Excalidraw

**Выбор: `@excalidraw/excalidraw` (MIT) как встраиваемый React-компонент.**

Обоснование — в первую очередь лицензионное. Главный конкурент, **tldraw**, технически лучше (быстрее, красивее, лучше стилус), но у него несвободная лицензия: запрещено отключать, прятать, удалять или изменять вотермарку и вмешиваться в проверку лицензионного ключа, и для продакшена нужен ключ: триальный, коммерческий или hobby; SDK работает в проде только с валидным активным ключом. Онлайн-школа — коммерческий проект, значит нужна платная лицензия. Ключи привязаны к доменам, и деплой на непокрытый домен считается нелицензированным.

Excalidraw: MIT-лицензия, ~129K звёзд, публикуется как npm-пакет `@excalidraw/excalidraw` для встраивания в веб-приложения. Нативно поддерживает изображения — то есть «прикрепить фото на доску во время урока» уже реализовано.

Важное ограничение, которое надо знать заранее: npm-пакет не содержит коллаборации — её реализует потребитель. Это и есть та работа, которую мы делаем сами (см. 3.4). Это не баг, а к лучшему: свой синк = свои права доступа, свои роли, свой лимит на ученика.

Что доработать поверх Excalidraw:
- Убрать/скрыть лишние инструменты (Mermaid, embed, библиотеки фигур) — упростить UI для школьника.
- Свои роли: учитель рисует всегда, ученики — по разрешению (глобально или пофамильно).
- Слой фона (слайд/фото) под элементами Excalidraw, недоступный для перемещения.
- Кнопка «следовать за учителем» (синхронизация viewport).
- Математические формулы (см. 3.6).

Технические заметки: по умолчанию Excalidraw тянет шрифты с CDN — для self-hosted нужно скопировать содержимое `node_modules/@excalidraw/excalidraw/dist/prod/fonts` в свою статику. Это обязательно: CDN может быть недоступен части учеников.

**Резервный план:** если через полгода упрёшься в производительность Excalidraw на больших досках — купить коммерческую лицензию tldraw. Абстрагируй доску за своим интерфейсом `IWhiteboardEngine`, чтобы замена стоила недели, а не месяца.

### 3.4 Синхронизация состояния: Yjs + Hocuspocus

**Выбор: Yjs (CRDT) + Hocuspocus как WebSocket-бэкенд.**

Почему CRDT, а не «широковещательные события»: доска — конкурентная структура. Команда Excalidraw сама описывала гонку: пир A добавляет элемент, пир B меняет цвет существующего — пир C теряет либо новый элемент, либо правку. CRDT решает это на уровне структуры данных, а не костылями.

Hocuspocus: v4 вышел под MIT-лицензией и больше не привязан к Node — переход на crossws позволил запускать один и тот же сервер на Node, Bun, Deno, Cloudflare Workers и Node с uWebSockets. Работает с любым Yjs-клиентом, и Yjs-документы не ограничены текстом — через них можно синхронизировать любые структурированные данные.

Готовая привязка Excalidraw↔Yjs существует: **`y-excalidraw`**. Важно понимать её ограничение: синхронизация идёт на уровне элемента массива, а не на уровне ключей элемента — но так же устроено и облачное решение самого Excalidraw. Для урока этого достаточно.

Что синхронизируем через Yjs (один Y.Doc на урок):

```
Y.Doc(lesson:{id})
├── Y.Map "meta"          → activePageId, presentationId, followTeacher, phase
├── Y.Map "pages"         → pageId → { backgroundAssetId, order, kind }
├── Y.Array "elements:{pageId}"  → элементы Excalidraw для страницы
├── Y.Map "permissions"   → userId → { canDraw, canSpeak, ... }
├── Y.Map "activity"      → активное задание, статус, дедлайн
└── awareness             → курсоры, viewport, «поднял руку», кто печатает
```

Что **не** через Yjs (а через обычный REST/WebSocket-события):
- Ответы учеников на задания (нельзя, чтобы ученик видел ответы соседа) — отдельный канал, сервер-авторитетно.
- Оценки, персональные данные.
- Чат (проще через Redis pub/sub, там нужна история и модерация).

Персистентность: расширение Hocuspocus сохраняет Y.Doc в Postgres (bytea) с дебаунсом 2–5 секунд + финальный снимок при закрытии урока.

### 3.5 Презентации: LibreOffice → PDF → изображения

**Требование:** учитель загружает `.pptx`, показ слайдов идёт без демонстрации экрана.

**Решение (проверенный отраслевой путь):**

```
.pptx/.docx/.odp  →  LibreOffice --headless  →  PDF  →  PNG (растр) + текстовый слой  →  S3
```

Ровно так делает BigBlueButton: когда загружен офисный документ, он конвертируется в PDF через LibreOffice, а затем PDF конвертируется в SVG; ход конвертации транслируется клиенту через Redis pub/sub.

Инструменты:
- **LibreOffice 25.x headless** (`soffice --headless --convert-to pdf`) — MPL 2.0
- **Poppler** (`pdftoppm`) — свободная библиотека рендеринга PDF, утилита `pdftoppm` конвертирует страницу PDF в растр. Лицензия GPLv2/GPLv3 — используем как **внешний бинарник в отдельном контейнере**, не линкуем в код. Это снимает вопросы GPL.
- **pdf.js** — библиотека Mozilla, рендерит PDF через HTML5 Canvas, лицензия Apache 2.0. Для PDF, загруженных напрямую, и для превью.

Альтернатива BBB для конвертации, если LibreOffice даст плохую вёрстку: Collabora Online (локально в докере или удалённо) как альтернативный скрипт конвертации.

**Что нужно принять как данность:** анимации и переходы PowerPoint не сохраняются. Ни один открытый рендерер их не поддерживает — ни `@jvmr/pptx-to-html`, где анимации, переходы, SmartArt, встроенное аудио/видео и 3D не поддерживаются, ни высокоточный `aiden0z/pptx-renderer` (Apache 2.0), где также не поддерживаются анимации/переходы, формулы OMML, полный EMF/WMF и заметки к слайдам. Это надо честно сказать методистам на старте: **анимации в слайдах не используем, вместо них — отдельные слайды или интерактивные блоки нашего движка.**

Формат хранения слайда:

| Что | Формат | Зачем |
|---|---|---|
| Основной рендер | PNG @2x (например, 2560×1440) | Быстро, предсказуемо, работает везде |
| Превью для ленты | WebP 320px | Лёгкая полоса миниатюр |
| Текстовый слой | JSON (из `pdftotext -bbox`) | Поиск по презентации, доступность, копирование текста учеником |

Опционально позже: SVG вместо PNG — вектор, масштабируется без пикселей, но LibreOffice-SVG иногда ломает шрифты. PNG @2x надёжнее для MVP.

Пайплайн загрузки (асинхронный, через BullMQ):
1. Учитель загружает файл → S3 (multipart, до 100 МБ) → задача в очередь.
2. Воркер-конвертер (изолированный контейнер, без сети наружу): antivirus-скан (ClamAV) → LibreOffice → PDF → pdftoppm → PNG/WebP → S3.
3. Прогресс транслируется в комнату через Yjs/WebSocket: `converting 7/24`.
4. По завершении презентация появляется в панели «Материалы урока».

Кеш: хеш файла → готовый набор слайдов. Одна и та же презентация на 40 уроках конвертируется один раз. BBB также поддерживает кеширование ассетов презентаций в S3/Minio.

### 3.6 Движок интерактивных заданий

Это самая объёмная часть. Здесь есть развилка.

#### Вариант A: H5P (взять готовое)

H5P — свободная и открытая технология под MIT-лицензией, десятки готовых типов контента (тесты, drag&drop, соответствия, интерактивное видео, заполнение пропусков), готовый редактор.

Для Node-стека есть **`@lumieducation/h5p-server`** — библиотека, дающая всё необходимое для создания собственных H5P-серверов на NodeJS, написанная на TypeScript и полностью типизированная. Активно поддерживается (v10.0.5, март 2026).

**Но три серьёзные проблемы:**

1. **Лицензия.** Сама библиотека `H5P-Nodejs-library` — **GPL-3.0**, включая фронтовые пакеты `h5p-webcomponents` и `h5p-react`. Для проприетарного SaaS это риск: серверная часть под GPL-3.0 (не AGPL) при работе по сети обязательств не создаёт, но JS-пакеты отдаются в браузер, и это уже распространение. Технически H5P-контент и так работает в iframe — изолируй H5P в отдельный сервис на поддомене, чтобы граница GPL не расползлась на твой код. **Обязательно проконсультируйся с юристом до того, как это станет фундаментом продукта.**
2. **Интеграция.** Это не готовое решение для standalone H5P-сервера — реализация HTTP-эндпоинтов, персистентности и вызова служебных функций остаётся на тебе. Это 3–4 недели работы, не выходные.
3. **UX редактора.** Редактор H5P — это редактор H5P. Методистам придётся под него подстраиваться, кастомизация ограничена.

#### Вариант B: свой движок (рекомендуется)

Пишем свой формат заданий и свой редактор. Дольше на старте, но:
- полный контроль над UX методиста (а это твоё главное конкурентное преимущество перед Zoom);
- задания живут прямо на доске/слайде, а не в iframe;
- нет лицензионных вопросов;
- ответы учеников — в твоей БД, в твоей схеме.

**Дизайн формата.** Не изобретай с нуля — опирайся на **QTI 3.0** (1EdTech), это отраслевой стандарт для тестов. Не обязательно реализовывать XML целиком — возьми модель взаимодействий и назови типы так же. Это даст:
- проверенный набор типов заданий (никакой методист не придумает то, чего нет в QTI);
- возможность в будущем импортировать/экспортировать в QTI;
- готовые опенсорсные плееры для сверки поведения: `agencyenterprise/qti-3-player` — библиотека на JS/TS, рендерящая QTI 3 XML, framework-agnostic, ставится через NPM; `pie-framework/pie-qti` — production-ready для QTI 2.x, инфраструктура QTI 3.0 готова, полная клавиатурная навигация и поддержка скринридеров по WCAG 2.2 AA.

**Решение: свой JSON-формат с семантикой QTI 3.** Схема в разделе 6.

**Правила модульности внутри монолита** (они и есть будущие швы для распила):

1. Модуль экспортирует **только** свой `service.ts`. Никто не импортирует чужой `repo.ts`.
2. Модуль не импортирует таблицы чужого модуля напрямую — только через его сервис.
3. Никаких циклических зависимостей между модулями (проверять через `dependency-cruiser` в CI).

### 4.3 Модель урока: единый холст

Главная продуктовая идея: **доска и презентация — это одна сущность, а не два режима.**

```
Урок (Lesson)
└── Холст (Canvas) — бесконечная лента страниц
    └── Страница (Page)
        ├── Фон (Background):
        │     • пусто (белая доска)
        │     • слайд презентации (PNG из S3)
        │     • изображение (загруженное фото/скан учебника)
        │     • PDF-страница
        │     • сетка / клетка / линейка / нотный стан / координатная плоскость
        ├── Слой аннотаций (Excalidraw elements) — рисование, текст, фигуры
        └── Слой интерактива (Activity) — задание, привязанное к странице
```

Что это даёт бесплатно:
- «Прикрепить фото на доску» = создать страницу с фоном-изображением или вставить image-элемент.
- «Режим презентации» = загрузили 24 слайда → создалось 24 страницы с фонами → учитель листает.
- «Порисовать поверх слайда» = обычное рисование, аннотации хранятся отдельно от фона.
- «Сохранить урок с пометками» = экспорт всех страниц в PDF (фон + аннотации).
- Ученик может отлистать назад, если разрешено, — не ломая показ у остальных.

## 5. Медиаполитика: как не убить сервер классом из 30 человек

**Это раздел, из-за которого падают самодельные платформы.** Наивная реализация «все камеры включены у всех» математически не работает.

### 5.1 Арифметика

Класс 30 человек, все с камерами 720p, полная сетка:
- 30 публикующих × 29 подписчиков = **870 видеопотоков**
- при ~1 Мбит/с даже на низком слое simulcast → **~870 Мбит/с исходящего трафика на ОДИН урок**
- порт 1 Гбит/с закончится на первом же классе

Аудио тоже не бесплатно: 30 × 29 = 870 аудиопотоков × ~35 кбит/с ≈ **30 Мбит/с**.

Ориентир от LiveKit: публичный бенчмарк на 16 ядрах показывает комнату 150 публикующих / 150 подписчиков в 720p при 85% CPU, но для небольших комнат на типичном порту 1 Гбит/с сеть обычно упирается раньше CPU: публикация 720p simulcast — примерно 2–2,5 Мбит/с, каждая подписка на видео стоит 1–2,5 Мбит/с в зависимости от того, какой слой simulcast получает подписчик.

### 5.2 Обязательные правила (в продукт, не в бэклог)

| Правило | Значение |
|---|---|
| Камера учителя | всегда, 720p, simulcast (720p/360p/180p) |
| Камера ученика | 360p максимум, публикуется **только когда ученик в активной сетке** |
| Одновременно видимых учеников | **не более 9** (активные говорящие + закреплённые учителем) |
| Остальные ученики | аватар + индикатор звука, видео не подписывается |
| Микрофон ученика | **выключен по умолчанию**, включается «поднятием руки» или разрешением учителя |
| Одновременно включённых микрофонов | не более 4 |
| Демонстрация экрана | максимум 1 одновременно, приоритет учителю, 1080p@5fps для документов / 720p@15fps для видео |
| `adaptiveStream` | включён — LiveKit сам понижает слой для маленьких плиток |
| `dynacast` | включён — не публиковать слои, на которые никто не подписан |

При этих правилах класс из 30 человек стоит примерно:
- учитель: 2 Мбит/с ↑, 30 подписок × 1,5 = **45 Мбит/с ↓**
- 9 видимых учеников: 9 × 0,5 = 4,5 Мбит/с ↑, 9 × 30 × 0,5 = **135 Мбит/с ↓**
- аудио (4 активных): пренебрежимо

**Итого ~180 Мбит/с на класс из 30** в режиме «Обсуждение».

### 5.2.1 Что это значит для одной машины

Порт 1 Гбит/с, из них резервируем ~250 Мбит/с на всё остальное (файлы, HTTP, запас на всплески). Остаётся **~750 Мбит/с на медиа**:

| Сценарий урока | Трафик на урок | Одновременно на 1 Гбит/с |
|---|---|---|
| Лекция, класс 30 (видео учеников не подписывается) | ~50 Мбит/с | **15** |
| Обсуждение, класс 30 (9 видео) | ~180 Мбит/с | **4** |
| Обсуждение, группа 12 (9 видео) | ~70 Мбит/с | **10** |
| Работа над заданием, любой размер | ~5 Мбит/с | **много** |
| Индивидуальный урок 1:1 | ~5 Мбит/с | **много** |

Реальное расписание — это смесь. Практическая планка MVP на одной машине:

> **8–12 одновременных уроков, 120–200 одновременных участников.**
> Цифра ориентировочная и **обязана быть подтверждена нагрузочным тестом** (`livekit-cli load-test`) до пилота, а не после.

Продуктовый рычаг, который стоит дешевле железа: **режим «Лекция» по умолчанию.** Он экономит 3–4× трафика. Переключение в «Обсуждение» — осознанное действие учителя, а не состояние по умолчанию.

### 5.3 Режимы урока (UI-переключатель у учителя)

| Режим | Что видно | Медиа-профиль |
|---|---|---|
| **Лекция** | доска/слайд на весь экран, учитель — плитка в углу | видео учеников не подписывается вовсе |
| **Обсуждение** | сетка до 9 плиток | активные говорящие |
| **Работа над заданием** | задание на весь экран, только аудио учителя | видео полностью выключено |
| **Опрос / у доски** | 1 ученик крупно + учитель | 2 видеопотока |

### 6.4 Правила проверки

- **Автопроверяемые типы** (1–5, 7–19, 22): проверка **на сервере**. Клиенту никогда не отправляются правильные ответы до сабмита. Это железное требование — иначе любой девятиклассник откроет DevTools.
- **Режим тренировки** (без оценки): допускается клиентская проверка для мгновенной обратной связи, но правильные ответы всё равно приходят только после ответа.
- **Ручная проверка** (6, 20, 21): попадает в очередь учителя с рубрикой.
- **Частичные баллы**: для `multiple_choice`, `matching`, `cloze_*`, `categorize` — по формуле `max(0, (верных − неверных) / всего)`.
- **Попытки**: `attemptsAllowed`, каждая попытка сохраняется отдельно, итог = лучшая/последняя (настройка).

### 6.5 Хранение ответов

```
attempt_id, material_id, lesson_id (nullable), user_id, question_id,
response JSONB, score NUMERIC, max_score NUMERIC,
auto_graded BOOL, graded_by UUID, graded_at, time_spent_ms,
attempt_number, submitted_at
```

Сырой `response` хранится всегда — чтобы можно было перепроверить после исправления ключа ответа.

## 7. Редактор для методистов

**Самый рискованный модуль. Планируй 8–12 недель.**

### 7.1 Принципы

1. **Методист — не программист.** Никаких JSON, никаких «выберите тип интеракции». Только «Добавить вопрос → Тест с одним ответом».
2. **WYSIWYG-превью всегда рядом.** Двухпанельный интерфейс: слева редактирование, справа — точно то, что увидит ученик. Не «предпросмотр в новой вкладке».
3. **Автосохранение + версии.** Никогда не терять работу. История версий с возможностью отката.
4. **Черновик ≠ опубликовано.** Учителя видят только опубликованные версии. Правка опубликованного материала создаёт новую версию, старая продолжает работать в уже проведённых уроках.
5. **Шаблоны.** «Проверочная работа 10 вопросов», «Разбор задачи», «Словарный диктант» — методист не начинает с чистого листа.

### 7.2 Экраны

| Экран | Содержание |
|---|---|
| Библиотека | Дерево: предмет → класс → тема. Фильтры, поиск, статусы (черновик/на ревью/опубликован), дублирование |
| Редактор материала | Слева — список блоков (drag&drop через dnd-kit), в центре — редактирование текущего блока, справа — превью глазами ученика |
| Редактор вопроса | Формулировка (Tiptap + MathLive + вставка изображений), тип задания, варианты/ключ, баллы, подсказка, обратная связь |
| Медиатека | Загруженные изображения/аудио/видео, с переиспользованием между материалами |
| Превью | Полноэкранный прогон материала как ученик, с проверкой и отображением баллов |
| Валидация | Перед публикацией: вопросы без правильного ответа, битые картинки, пустые блоки, нулевые баллы |

### 7.3 Панель учителя во время урока

- Открыть материал из библиотеки → показать на текущей странице холста.
- Кнопка «Запустить для класса»: задание уходит **каждому ученику индивидуально** (не через доску!), таймер, дедлайн.
- Живая панель прогресса: кто открыл / кто ответил / кто застрял (сколько времени на вопросе).
- Агрегированные результаты по вопросу: «17 из 24 выбрали вариант B» — гистограмма, чтобы сразу разобрать ошибку.
- Разбор: показать правильный ответ всем, вынести чей-то ответ на доску (анонимно или с именем).

## 10. Инфраструктура: один сервер

### 10.1 Железо

**Требование №1 — безлимитный канал 1 Гбит/с.** Это важнее ядер, важнее памяти, важнее всего остального. Причина в §10.2.

Рекомендуемая конфигурация (dedicated, не VPS):

| Параметр | Минимум | Рекомендуется |
|---|---|---|
| CPU | 6 физических ядер | **8–14 ядер** (Ryzen 7/9 или i5-13500/i7) |
| RAM | 32 ГБ | **64 ГБ** |
| Диск | 2×512 ГБ NVMe (RAID1) | **2×1 ТБ NVMe (RAID1)** |
| Сеть | **1 Гбит/с unmetered** | 1 Гбит/с unmetered |
| ОС | Ubuntu 24.04 LTS | Ubuntu 24.04 LTS |

Провайдеры: **Hetzner** (линейки AX/EX, ~€45–75/мес), **OVH**, **Selectel** / **Timeweb** (если нужна юрисдикция РФ, см. §10.8).

**Итого: €50–90/мес за всю платформу.** Против €250–400 в исходной распределённой схеме.

**Вторая площадка — обязательна, но требования к ней скромные.** Её задачи: принимать `restic`-бэкапы и зеркало git. CI на ней не крутится (§10.9), поэтому подойдёт почти что угодно с диском и SSH:

- домашний ПК или NAS школы — €0, если уже есть;
- Raspberry Pi 5 с внешним HDD — €150 разово;
- самый дешёвый VPS у **другого** провайдера — €5/мес, если дома нет стабильного интернета.

Внешний uptime-мониторинг на неё вешать **не надо**: для этого есть бесплатный UptimeRobot, и внешний сервис здесь объективно лучше собственного (§10.11). Почему основной сервер всё-таки арендуется — §10.14.

### 10.2 Почему dedicated с unmetered, а не облако

Это не вопрос вкуса, а вопрос порядка величины. Посчитаем месячный исходящий трафик для скромного расписания:

```
6 параллельных уроков × 180 Мбит/с  = 1080 Мбит/с ≈ 135 МБ/с
135 МБ/с × 3600 с                    = 486 ГБ в час
486 ГБ × 6 учебных часов             = 2,9 ТБ в день
2,9 ТБ × 20 учебных дней             ≈ 58 ТБ в месяц
```

| Хостинг | Стоимость 58 ТБ egress/мес |
|---|---|
| AWS EC2 ($0,09/ГБ) | **≈ $5 200** |
| Google Cloud / Azure | сопоставимо |
| DigitalOcean / Linode (после включённого лимита) | ≈ $580 |
| **Hetzner dedicated, unmetered** | **€0 сверх аренды** |

Видеоплатформа на облаке с метрируемым трафиком экономически невозможна для одной школы. **Проверь слово «unmetered» в договоре перед оплатой.** Некоторые провайдеры пишут «unlimited», а в мелком шрифте — fair use с троттлингом до 100 Мбит/с.

### 10.3 Раскладка ядер (обязательно)

Главный риск монолита на одной машине: **конвертация PPTX съедает CPU и у всего класса начинает заикаться звук.** Медиа-обработка чувствительна к джиттеру планировщика, а LibreOffice — это всплеск на 100% нескольких ядер на 30–60 секунд.

Решение — жёсткое разделение ядер через `cpuset` в docker-compose. Пример для 8-ядерной машины:

| Контейнер | `cpuset` | `cpu_quota` | Комментарий |
|---|---|---|---|
| `livekit` | `0-3` | — | **эксклюзивно**, ни с кем не делится |
| `app` | `4-5` | — | Node, event loop |
| `postgres` + `redis` | `6` | — | |
| `converter` | `7` | `0.8` | не больше 80% одного ядра, даже если очередь |
| `caddy`, мониторинг | `7` | `0.2` | |

```yaml
services:
  livekit:
    cpuset: "0-3"
    network_mode: host          # обязательно: UDP-диапазон
  app:
    cpuset: "4-5"
  converter:
    cpuset: "7"
    cpu_quota: 80000            # 0.8 CPU при period=100000
    mem_limit: 3g
    network_mode: none          # НЕТ СЕТИ: парсим недоверенные файлы
    read_only: true
    tmpfs: [/tmp]
```

Дополнительно: очередь конвертации с `concurrency: 1` и, если школа согласна, **окно конвертации вне учебных часов** для массовых загрузок.

### 10.4 Запись уроков на одной машине

Честно: **запись — единственная функция, которая на монолит нормально не помещается.**

RoomComposite egress потребляет от 2 до 6 CPU и запускает внутри headless-Chrome для композитинга. Одна запись съест половину машины и убьёт качество звука на всех остальных уроках.

Три варианта, в порядке предпочтения:

1. **Отложить запись до Этапа 6** и там же завести под неё вторую машину (€40–60/мес). Рекомендуемый путь. Пилот проживёт без записи.
2. **Track Egress вместо RoomComposite** — писать отдельные дорожки (аудио учителя + видео учителя) без композитинга. Одиночная дорожка стоит 1× базового CPU против 3× у room-composite. Сшивать в один файл потом, ночью, через ffmpeg. Дёшево, но результат — не «как выглядел урок».
3. **Клиентская запись** — `MediaRecorder` в браузере учителя, загрузка файла после урока. Ноль нагрузки на сервер, но зависит от машины учителя и легко теряется.

**Решение для MVP: варианта 1.** Записи в v1 нет; в UI кнопка «Записать урок» помечена как «скоро».

### 10.5 Правила эксплуатации LiveKit

- **Redis** нужен LiveKit'у для координации между инстансами; при одном инстансе он не обязателен, но всё равно уже есть в стеке для BullMQ — подключай сразу, чтобы потом не менять конфиг.
- **`network_mode: host`** для контейнера LiveKit. Пробрасывать UDP-диапазон 50000–60000 через docker-proxy — верный способ получить необъяснимые потери пакетов.
- **Порты открыть заранее:** 7880 (WS/HTTP), 7881 (TCP fallback), UDP 50000–60000, 3478 (TURN/UDP), 5349 (TURNS/TCP). Неверная экспозиция UDP-диапазона — самая частая ошибка развёртывания.
- **`ufw` + правила.** На одном сервере firewall — единственная граница. Наружу торчат только 80, 443, 7880, 7881, 3478, 5349, UDP 50000–60000 и SSH на нестандартном порту с ключами.
- **Бэкап состояния комнат не нужен** — оно эфемерно. Практическая стратегия: держать `docker-compose.yml`, `livekit.yaml`, `Caddyfile` и конфиг TURN в git, чтобы окружение пересобралось на новом железе за минуты.
- **Метрики.** Осторожно с именами: `*_total` у LiveKit (`livekit_room_total`, `livekit_track_published_total`) — это gauge текущих значений, а не counter, и `rate()` по ним даёт мусор. Настоящие counter'ы называются `*_counter`.
- **Нагрузочное тестирование до продакшена.** Для LiveKit оно важнее, чем для обычного stateless-сервиса: стоимость обработки медиа растёт с числом участников и разрешением так, что по графикам CPU это легко недооценить. Инструмент: `livekit-cli load-test`.

### 10.6 Когда и в каком порядке распиливать

Не раньше, чем упрёшься. Триггеры и действия — в этом порядке:

| Триггер | Что выносим | Сложность |
|---|---|---|
| Исходящий трафик > 700 Мбит/с в пик **или** CPU LiveKit > 70% | **LiveKit + coturn** на вторую машину | 1 день: сменить URL и ключи в конфиге. Клиент подключается по `wss://media.школа.ru` |
| Нужна запись уроков | **LiveKit Egress** на третью машину | 2 дня |
| `/data/assets` > 1 ТБ **или** нужно разнести хранение | **Хранилище** → SeaweedFS (Apache 2.0) на второй машине | 1 день: переключить `StorageAdapter` с `LocalFS` на `S3` |
| CPU Postgres > 60% **или** нужен PITR без ручной работы | **Postgres** на managed | 1 день |
| Один процесс Node не тянет | **Hocuspocus** отдельным процессом, затем `app` в 2–3 инстанса за Caddy | 3–5 дней (нужен sticky-роутинг по `lesson_id`) |

**Важно:** первый шаг (вынос медиа) закрывает ~80% возможных проблем и делается за день. Именно поэтому монолит здесь безопасен — стоимость ошибки низкая.

Чтобы эти шаги оставались однодневными, соблюдай с первого дня:
- все внешние адреса — через переменные окружения, ни одного захардкоженного `localhost`;
- доступ к файлам — только через `StorageAdapter`, ни одного `fs.readFile` в бизнес-логике;
- никакого состояния в памяти процесса, кроме кешей, которые можно потерять (Y.Doc в памяти — можно, он персистится в Postgres);
- правила модульности из §4.1.1.

### 10.7 Бэкапы и восстановление

Один сервер = одна точка отказа. Это приемлемо для MVP **только** при работающих бэкапах.

| Что | Как | Куда | Частота |
|---|---|---|---|
| PostgreSQL | `pg_dump` + WAL-архивация (`pgBackRest` или `wal-g`) | локально `/data/backups` + `restic` на вторую площадку | дамп 1/сутки, WAL непрерывно |
| `/data/assets` | `restic` (дедупликация + шифрование) | вторая площадка | 1/сутки |
| Конфиги и код | git | **GitHub** + зеркало на вторую площадку (§10.9) | при каждом `push` |
| Снапшот всей машины | `restic`/`borg` образ + средствами провайдера | вторая площадка | 1/неделя |

**Вторая площадка** — физически другое место: домашний ПК, NAS школы, Raspberry Pi с внешним HDD, дешёвый VPS у другого провайдера. Требования: 2 ТБ диска, любой канал, `restic`-репозиторий по SSH.

**Правило 3-2-1:** три копии, два типа носителя, одна вне основной площадки. `restic` шифрует на клиенте, поэтому целевое хранилище может быть недоверенным.

**Обязательно:** раз в месяц — учебное восстановление из бэкапа на чистой машине с секундомером. Бэкап, из которого ни разу не восстанавливались, — это не бэкап.

Целевые показатели MVP: **RPO ≤ 24 часа** (для файлов) и **≤ 5 минут** (для БД благодаря WAL), **RTO ≤ 4 часа**.

Отдельно: доска урока живёт в памяти Hocuspocus и персистится в Postgres с дебаунсом. Перезапуск `app` во время урока = потеря последних 2–5 секунд рисования. Для MVP приемлемо, но **деплой только вне учебных часов** — вынести в правило.

### 10.8 Что мониторить с первого дня

| Метрика | Порог алерта |
|---|---|
| Исходящий трафик сервера | > 600 Мбит/с (80% от медиа-бюджета) |
| CPU ядер 0-3 (LiveKit) | > 70% |
| Load average всей машины | > числа ядер |
| Свободное место на `/data` | < 20% |
| P95 задержка сигналинга | > 300 мс |
| Доля соединений через TURN | > 20% (значит проблемы с UDP) |
| Packet loss участников | > 3% |
| Event loop lag процесса `app` | > 100 мс |
| Очередь конвертации PPTX | > 5 задач или > 3 мин |
| Ошибки автосохранения ответов | любая |
| Внешний uptime-чек с чужого VPS | 2 неудачи подряд |

Стек — целиком self-hosted, всё влезает в ту же машину:

| Задача | Инструмент | Лицензия | Ресурсы |
|---|---|---|---|
| Метрики | **Prometheus** + `node_exporter`, `postgres_exporter` | Apache 2.0 | ~500 МБ |
| Дашборды и алерты | **Grafana** | AGPL (self-host — без обязательств) | ~300 МБ |
| Логи | **Loki** или **VictoriaLogs** (легче) | AGPL / Apache 2.0 | ~300 МБ |
| Ошибки фронта и бэка | **GlitchTip** | MIT | 512 МБ – 2 ГБ |
| Внешний uptime | **UptimeRobot free** (50 мониторов, интервал 5 мин) | внешний, бесплатный | €0 |
| Доставка алертов | **ntfy** (свой push) + пуш от UptimeRobot | Apache 2.0 | ~50 МБ |

**GlitchTip вместо Sentry — ключевая замена.** Он реализует протокол Sentry SDK, поэтому обычные пакеты `@sentry/*` работают без изменений: меняешь только DSN. При этом поднимается на четырёх контейнерах вместо сорока и комфортно живёт на 512 МБ.

Self-hosted Sentry на ту же машину не поставить: его открытая сборка требует 40+ контейнеров и от 16 ГБ RAM как пола — ровно та операционная тяжесть, ради ухода от которой GlitchTip и был создан. Для справки о лицензии: с 2023 года Sentry под FSL — бесплатно запускать, менять и распространять для любых целей, кроме конкурирующих коммерческих продуктов, и каждый релиз через два года конвертируется в Apache 2.0. Юридически школе можно; операционно — нет.

Ограничение GlitchTip, которое надо знать заранее: session replay, профилирование и виджеты обратной связи не поддерживаются и **отваливаются молча**. Ошибки, breadcrumbs, релизы, окружения и контекст пользователя работают.

**Про внешний uptime отдельно.** Это единственное место, где внешний сервис **лучше** своего: проверка доступности обязана идти из другой сети. Свой Uptime Kuma на домашнем ПК будет слать ложные тревоги каждый раз, когда моргнёт домашний интернет. Бесплатного UptimeRobot достаточно; если он завтра закроется — заменяется за пять минут, урок не заметит.

**Оповещения:** Grafana Alerting → ntfy → приложение на телефоне, плюс пуш от UptimeRobot как независимый канал. Без Telegram, без PagerDuty, без Slack.

### 10.9 CI/CD

Git-хостинг и CI — это **build-time**, не runtime. Если они лежат, урок всё равно идёт: ты просто не можешь задеплоить новую версию. По правилу §10.10 это разрешённая внешняя зависимость, если она бесплатна.

**Решение: GitHub Free.** Бесплатный план даёт неограниченные приватные репозитории с неограниченным числом соавторов, 2 000 Linux-минут Actions в месяц и 500 МБ хранилища пакетов. Для соло-разработчика с пятиминутной сборкой это ~400 сборок в месяц — с большим запасом. По умолчанию лимит трат равен нулю, поэтому при превышении джобы просто перестают запускаться, а не выставляют счёт.

Это экономит **неделю на Этапе 0** и ~2 часа в месяц против self-hosted Forgejo. Ровно та экономия, ради которой правило §10.10 и написано.

**Реестр контейнеров не нужен вовсе.** Монолит на одной машине собирается прямо на ней:

```
GitHub Actions:  lint → typecheck → test          (проверка качества)
Деплой:          ssh на прод → git pull
                 → docker compose up -d --build   (сборка на месте)
                 → migrate
```

Это снимает сразу три вопроса: 500 МБ лимита GitHub Packages, неопределённость с будущей тарификацией GHCR (он «пока бесплатен», с обещанием предупредить за месяц) и лишний шаг push/pull образов. Сборка идёт вне учебных часов, когда ядра свободны.

**Две страховки, обе бесплатные и обязательные:**

1. **Зеркало git на второй площадке.** Одна строка в `.git/config`, и `git push` уходит в оба места сразу:
   ```
   git remote set-url --add --push origin git@github.com:user/school.git
   git remote set-url --add --push origin backup@nas.local:/srv/git/school.git
   ```
   GitHub закрылся, заблокировал аккаунт, потерял репозиторий — у тебя полная копия истории. Стоимость: ноль.

2. **`pnpm-lock.yaml` в git + `--frozen-lockfile` всегда.** Это уже даёт воспроизводимость сборки. Дополнительно: раз в месяц `pnpm store prune && tar czf vendor-snapshot.tgz ~/.pnpm-store` на вторую площадку — на случай удалённого из npm пакета.

**Чего НЕ делаем** (было в версии 1.2, вычеркнуто по правилу §10.10): Forgejo, Verdaccio, `registry:2` pull-through cache, self-hosted Renovate. Всё это решало проблему «а вдруг npm недоступен», которая для школьной платформы стоит одной ночи неудобства раз в несколько лет, а обходится в неделю работы плюс постоянное обслуживание. Лок-файл и зеркало git закрывают тот же риск на 95% бесплатно.

Остальное:

- Миграции БД — отдельным шагом **до** запуска новой версии, всегда обратно совместимые (expand/contract), чтобы откат не ломал схему.
- **Staging обязателен**, но может быть тем же сервером: второй `docker-compose` с другим набором портов и префиксом БД. WebRTC ломается способами, которые локально не воспроизводятся.
- **Деплой-окно:** только вне учебных часов. Скрипт деплоя должен проверять, нет ли активных уроков (`SELECT count(*) FROM lessons WHERE status='live'`), и отказываться, если есть, — с флагом `--force` для аварийных случаев.
- Один скрипт `./deploy.sh` в репозитории. Ни в коем случае не ручные команды по памяти.

### 10.10 Правило допуска внешнего сервиса

Формализация требования из §1.2. Прежде чем взять любой внешний сервис, три вопроса подряд:

```
1. Он платный (сейчас или станет платным)?              → ДА → отказ
2. Урок остановится или деградирует, если он ляжет?     → ДА → отказ
3. Уход от него потребует переделки архитектуры?        → ДА → отказ
                                                        → всё «нет» → можно
```

Вопрос №2 — главный. Он делит всю систему на три слоя:

| Слой | Что входит | Если ляжет | Политика |
|---|---|---|---|
| **Runtime** — критический путь урока | app, Postgres, Redis, LiveKit, coturn, хранилище файлов, TLS, DNS, хостинг | **урок встал** | только своё; внешнее — лишь неустранимое (§10.13) |
| **Build-time** | git, CI, реестры пакетов | нельзя задеплоить, уроки идут | **можно внешнее, если бесплатно** |
| **Observability** | метрики, ошибки, uptime, алерты | летишь вслепую, уроки идут | можно внешнее, но своё почти ничего не стоит |

Практический смысл: **бороться надо за runtime, а не за все имена в стеке.** Self-hosted Forgejo не делает уроки надёжнее ни на один процент — он делает надёжнее твой деплой, который и так не критичен. Зато self-hosted LiveKit делает: без него платформы просто нет.

#### 10.11.1 Почему Google Fonts — исключение

По правилу он проходит: бесплатный, некритичный. Но проверка вопросом №2 даёт «да», и вот почему:

- **Шрифты блокируют рендер.** Пока `fonts.googleapis.com` не ответил, ученик видит пустую или прыгающую страницу. Это прямо на пути открытия урока.
- **Excalidraw и так требует самохостинга шрифтов.** При self-hosted-развёртывании нужно скопировать содержимое `node_modules/@excalidraw/excalidraw/dist/prod/fonts` в свою статику. Половина работы всё равно уже сделана.
- **Юридический риск, не гипотетический.** В январе 2022 года Landgericht München I (дело 3 O 17493/20) постановил, что загрузка Google Fonts с CDN без согласия нарушает GDPR: IP-адрес — персональные данные, а «легитимный интерес» суд отклонил именно потому, что самохостинг доступен и ничего не стоит. Истцу присудили €100, а за повторные нарушения предусмотрены санкции до €250 000. Решение породило волну автоматизированных претензий к мелким сайтам. Мы обрабатываем данные несовершеннолетних — это худшая категория для такого риска.
- **Исправление занимает 10 минут.** Скачать `.woff2`, положить в `/fonts`, написать `@font-face`. Самохостинг при этом ещё и быстрее: не нужен лишний DNS-lookup и соединение с чужим сервером.

**То же самое и по той же причине:** KaTeX, MathJax, иконки, любые JS-библиотеки с CDN. Всё в бандл, всё со своего домена.

> **Тридцатисекундная проверка автономности рантайма:** открой боевой сайт, DevTools → Network, фильтр по домену. Единственный домен в списке должен быть твой. Ни `fonts.googleapis.com`, ни `cdnjs`, ни `unpkg`, ни `google-analytics`.

#### 10.11.2 Почта убрана из архитектуры

Собственный SMTP на свежем IP — месяцы борьбы за репутацию с Gmail и Mail.ru. Платный сервис — нарушение правила. Решение: **почты нет вообще.**

- Аккаунты заводит администратор школы, в том числе массово, CSV-импортом класса.
- Пароль ученик получает офлайн, от классного руководителя — как логин от электронного дневника.
- Забыл пароль → администратор сбрасывает из админки. Ссылки на почту нет.
- Уведомления о начале урока не нужны: есть расписание.

Это не компромисс, а более правильная модель для замкнутого контура одной школы: меньше кода, меньше поверхности атаки (нет флоу восстановления — нечего эксплуатировать), ноль зависимостей.

Если почта всё-таки понадобится — использовать **существующий почтовый ящик школы** через SMTP-relay. Это не новый сторонний сервис, а то, чем школа уже пользуется.

### 10.13 Неустранимый минимум

После всех замен снаружи остаются ровно три сущности. Это не недоработка, а физика интернета.

| Зависимость | Почему неустранима | Как снизить риск |
|---|---|---|
| **Магистральный провайдер / хостинг** | Сервер не подключается к интернету сам по себе. «Своё железо дома» этого не решает — оно просто меняет одного провайдера на другого, более слабого (§10.14) | Всё описано в `docker-compose.yml`, данные в `restic`. Переезд к другому провайдеру = `restore` + смена A-записи |
| **Регистратор домена** | DNS иерархичен, домен второго уровня выдаёт регистратор | Регистратор, не связанный с хостером. Блокировка переноса, оплата на 5+ лет вперёд, 2FA |
| **Публичный CA (TLS)** | Браузеры доверяют только публичным CA, а `getUserMedia` и WebRTC требуют secure context. Свой CA = красная плашка у каждого ученика и неработающее видео | Let's Encrypt через Caddy, запасной ACME-провайдер (ZeroSSL, Buypass) прописан заранее |

**Критерий настоящей независимости — не длина списка, а один вопрос:**

> *«Если провайдер завтра закроется, сколько времени мне нужно, чтобы поднять всё на новом железе?»*
> Ответ «≤ 4 часа» = ты независим. Ответ «не знаю» = проблема не в провайдере, а в отсутствии проверенного бэкапа и скрипта развёртывания (§10.7).

### 10.14 Почему сервер всё-таки арендованный, а не свой

Вопрос возникает у всех, кто хочет полной независимости. Разбор по трём вариантам:

| | **Аренда dedicated** ✅ | **Колокация** | **Сервер дома / в школе** |
|---|---|---|---|
| Железо | провайдера | твоё | твоё |
| Канал | 1 Гбит/с unmetered, симметричный | 1 Гбит/с симметричный | **50–100 Мбит/с вверх, асимметричный** |
| Вход | €0 | €1500–3000 | €1500–3000 + UPS |
| В месяц | €50–90 | €80–200 | €0 сверх интернета |
| Питание, резервный канал | ЦОД, N+1 | ЦОД, N+1 | **розетка, ничего** |
| DDoS-защита | обычно входит | зависит от ЦОД | **нет** |
| Диск умер в 3 ночи | техник провайдера | едешь сам | встаёшь сам |
| **Годится?** | **да** | через 2–3 года | **нет** |

**Домашний вариант не работает по арифметике, а не по идеологии.** Класс из 30 в режиме «Обсуждение» — ~180 Мбит/с **исходящего** трафика (§5.2). Домашний и офисный интернет почти всегда асимметричный: 500 вниз / 50 вверх. Пятьдесят мегабит — это один урок на десять человек, впритык. Добавь серый IP за CGNAT, отсутствие обратной DNS-зоны, суточные обрывы, ноль DDoS-фильтрации и обязанность самому чинить железо ночью — и «полная независимость» превращается в зависимость от домашнего провайдера, у которого SLA нет вовсе.

**Колокация имеет смысл через 2–3 года**, когда трафик стабилен и €2000 за сервер окупаются за полтора года аренды. Не сейчас: пока конфигурация меняется, аренда — это гибкость.

**Аренда — это не потеря независимости.** Провайдер даёт розетку, канал и IP. Всё остальное твоё: твоя ОС, твой софт, твои данные, твои ключи. Настоящая независимость — не «ни от кого не завишу», а **«могу уйти за четыре часа и ничего не потеряю»**.

### 10.15 Юрисдикция данных

Если ученики — граждане РФ, персональные данные (ФИО, email, записи уроков с лицами и голосом) по 152-ФЗ должны первично храниться на серверах в РФ. Записи уроков — это биометрия в широком толковании. **Решить до выбора хостинга**, миграция потом стоит дорого.

Для монолита это решение особенно критично: переезд одного сервера с 500 ГБ данных — это ночь простоя, а не «переключим DNS».

При хостинге в ЕС/РФ — проверить latency и доступность для целевой аудитории, включая TURN. Прогнать `ping` и тестовый звонок с реальных ученических каналов до подписания договора с хостером.

### 12.1 Принцип очерёдности: по стоимости нагрузки

Этапы упорядочены **не по продуктовой логике, а по тому, сколько ресурсов сервера добавляет каждый.** Каждый этап вводит ровно один новый класс нагрузки, и между этапами стоит гейт — нагрузочная проверка, без прохождения которой дальше не идут.

Причина: на одной машине две трети всей нагрузки платформы приходятся на два этапа из одиннадцати (видео учителя и видео учеников). Если делать их первыми, отладка доски и заданий идёт на фоне забитого канала, и непонятно, что именно тормозит.

| Этап | Что добавляет | Трафик на 10 уроков | Недель |
|---|---|---|---|
| **Э0** Скелет: auth, CRUD, деплой, бэкапы, мониторинг | HTTP | ~0 | 3 |
| **Э1** Комната без медиа: WS, presence, чат, права | WebSocket | < 1 Мбит/с | 1,5 |
| **Э2** Аудио: LiveKit, микрофоны, проверка устройств | Opus | ~30 Мбит/с | 2 |
| **Э3** Доска: Yjs, Excalidraw, страницы, изображения | RAM процесса | < 2 Мбит/с | 4 |
| **Э4** Слайды: конвертер, страницы-фоны, навигация | всплески CPU | ~0 в уроке | 2,5 |
| 🎯 **MVP: голос + доска + слайды. Пилот.** | | | **3 мес** |
| **Э5** Видео учителя | 1 паблишер | **~300 Мбит/с** | 1,5 |
| **Э6** Видео учеников: сетка ≤9, режимы урока | 9 паблишеров | **~700 Мбит/с** | 2 |
| **Э7** Демонстрация экрана | 1 паблишер | +50 Мбит/с | 1 |
| **Э8** Задания: плеер, 10 типов, серверная проверка | HTTP + WS | +2 Мбит/с | 6 |
| **Э9** Редактор для методистов | ничего | ~0 | 10 |
| **Э10** Запись уроков | **2–6 ядер** | вторая машина | 2 |
| **Э11** Достройка | разное | | 4 |

**Итого ~9,5 месяцев чистой разработки, с коэффициентом на реальность — 11–12.**

### 12.2 Что даёт такой порядок

- **Первый настоящий урок — на 3-м месяце, а не на 4-м.** Голос + общая доска + слайды — это полноценный урок; видео не является ядром продукта.
- **Видео учителя добавляется за полторы недели**, потому что вся инфраструктура (LiveKit, токены, права, проверка устройств, сетка участников) уже построена и отлажена на дешёвом аудио.
- **Потолок платформы измеряется на Э6**, когда всё остальное стабильно. Если 4 класса по 30 не влезают — это точно ограничение канала, а не баг, и лечится выносом LiveKit на вторую машину за один день (§10.6).
- **Э4 — главный гейт монолита.** Конвертация PPTX во время активных уроков не должна поднимать джиттер аудио. Не прошёл — не идёшь дальше.

### 12.3 Порядок урезания, если сроки поехали

1. Э11 целиком — это и есть буфер.
2. Э10 (запись) — школа проживёт без записей полгода.
3. Э9 — пять типов заданий в редакторе вместо десяти.
4. Э7 (демонстрация экрана) — учитель покажет через слайды.
5. Э6 (видео учеников) — режим «Лекция» закрывает 80% уроков.

**Не урезать никогда:** бэкапы с проверенным восстановлением (Э0.10), жизненный цикл Y.Doc (Э3.3), раскладка ядер (Э4.2), тесты движка проверки заданий (Э8.3). Каждый пункт — это либо потеря данных, либо тихая порча оценок учеников, либо сорванный урок.

Всё остальное в стеке — €0: LiveKit, Postgres, Redis, coturn, Caddy, GlitchTip, Prometheus, Grafana, Loki, ntfy, GitHub Free, GitHub Actions, UptimeRobot free, npm, Docker Hub.

### 14.2 Что взято бесплатным снаружи (и почему это нормально)

| Сервис | Слой | Если исчезнет |
|---|---|---|
| GitHub Free + Actions | build | Переключаешься на зеркало на второй площадке. Уроки идут |
| npm, Docker Hub | build | Лок-файл + снимок стора. Уроки идут |
| UptimeRobot free | observability | Заменяется за 5 минут. Уроки идут |
| Let's Encrypt | **runtime** | Запасной ACME-провайдер в конфиге Caddy |
| NTP-пулы | runtime (косвенно) | `chrony` на пул, не на одного вендора |

Общее у первых трёх: **ни один не может остановить урок и ни один не может выставить счёт.** Это и есть критерий допуска.

### 14.3 Что было в прежних версиях ТЗ и вычеркнуто

| Позиция | Причина |
|---|---|
| LiveKit Cloud | платный, критический путь. 58 ТБ/мес по $0,12/ГБ ≈ $7 000/мес |
| Managed PostgreSQL | платный, критический путь |
| S3 / Backblaze под файлы урока | платный, критический путь |

| Resend / Postmark | платный. Почта убрана из архитектуры (§10.11.2) |
| Sentry Cloud, Grafana Cloud | free tier проходит по правилу, но свои варианты уже в стеке и не берут лишних ресурсов |

| **Forgejo, Verdaccio, registry-cache, self-hosted Renovate** | были в версии 1.2. **Вычеркнуты по правилу §10.10:** решают некритичную проблему ценой недели работы. Экономия — неделя на Этапе 0 |
| Коммерческая лицензия tldraw | платная. Excalidraw (MIT) |

### 14.4 Единственное, что остаётся к обсуждению

**Коммерческая лицензия tldraw** — если через полгода Excalidraw не потянет по производительности или UX стилуса. Формально это нарушение правила «ничего платного», но с оговоркой: это не подписка на инфраструктуру, а исходники, которые лежат у тебя. Продукт от доступности вендора не зависит — только от разового платежа. Свободной альтернативы того же уровня нет.

Решать не раньше, чем упрёшься. Абстракция `IWhiteboardEngine` (§3.3) делает замену вопросом недели.

## 15. Чего не делать

1. **Не форкать BigBlueButton или Jitsi Meet.** Разверни BBB на день, проведи уроки, укради идеи — но пиши своё.
2. **Не писать свой SFU.** Даже не думать.
3. **Не пытаться сохранить анимации PowerPoint.** Нет открытого решения. Скажи методистам заранее.
4. **Не начинать с движка заданий.** Он самый интересный и самый бесполезный без работающих уроков.
5. **Не хранить состояние доски в БД на каждый штрих.** Yjs в памяти + дебаунс 2–5 сек.
6. **Не использовать Next.js/SSR.** Приложение реалтайм-клиентское, SSR только мешает.
7. **Не делать мультитенантность в v1.** Оставь `school_id` в схеме и забудь.
8. **Не отправлять правильные ответы на клиент.** Никогда.
9. **Не включать камеры всем по умолчанию.** См. раздел 5.
10. **Не пропускать пилот на 4-м месяце.** Полгода разработки без реальных уроков = полгода в неверную сторону.
11. **Не разносить свой код на сервисы.** Один процесс Node. Микросервисы соло — это способ потратить месяц на инфраструктуру вместо продукта. Швы для будущего распила — это правила модульности (§4.1.1), а не сетевые вызовы.
12. **Не брать Kubernetes.** Ни k8s, ни k3s, ни Nomad. `docker compose` для 7 контейнеров на одной машине — это ровно тот инструмент.
13. **Не запускать конвертер и медиа на общих ядрах.** См. §10.3. Это не микрооптимизация, это разница между «звук нормальный» и «урок сорвался».
14. **Не брать облачный VPS с метрируемым трафиком.** См. §10.2. Счёт в $5 000 за месяц закроет проект.
15. **Не откладывать бэкапы «на потом».** На одной машине это не гигиена, а единственная страховка. Восстановление проверить до пилота, а не после инцидента.
16. **Не ставить сервер дома или в офисе школы.** Асимметричный канал (50 Мбит/с вверх) не выдержит и одного класса. См. §10.11.
17. **Не тянуть ничего с чужих CDN.** Ни шрифты, ни KaTeX, ни иконки — даже «бесплатные и безобидные». Google Fonts блокирует рендер и является установленным GDPR-риском (§10.11.1). Проверка — DevTools → Network, должно быть пусто по чужим доменам.
18. **Не делать свой CA для TLS.** Браузер покажет красную плашку каждому ученику, а WebRTC вообще не запустится без secure context. Let's Encrypt — неустранимая зависимость, смирись (§10.13).
19. **Не поднимать свой SMTP ради восстановления пароля.** Убери почту из архитектуры целиком, пароли сбрасывает администратор.
20. **Не хостить у себя то, что бесплатно снаружи и не влияет на урок.** Свой Forgejo, свой Verdaccio, свой Uptime Kuma — это неделя работы и постоянное обслуживание ради риска, который стоит одной ночи неудобства раз в несколько лет. Правило §10.10 существует именно для этого. Независимость — короткий список, который ты знаешь наизусть, а не «у меня всё своё».

## Приложение Б. Скелет `docker-compose.yml`

Не рабочий конфиг, а карта того, что где живёт. Значения `cpuset` — под 8-ядерную машину, пересчитать под свою.

```yaml
name: school

x-logging: &logging
  logging:
    driver: json-file
    options: { max-size: "50m", max-file: "5" }

services:
  caddy:
    image: caddy:2-alpine
    restart: unless-stopped
    ports: ["80:80", "443:443"]
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy_data:/data
    cpuset: "7"
    <<: *logging

  app:                                   # ← МОНОЛИТ
    build: ./apps/api
    restart: unless-stopped
    cpuset: "4-5"
    mem_limit: 8g
    environment:
      DATABASE_URL: postgres://app:***@postgres:5432/school
      REDIS_URL: redis://redis:6379
      STORAGE_DRIVER: local            # local | s3
      STORAGE_PATH: /data/assets
      LIVEKIT_URL: ws://livekit:7880   # наружу — wss://<домен>/rtc
      LIVEKIT_API_KEY: ***
      LIVEKIT_API_SECRET: ***
      CONVERTER_URL: http://converter:8080
      PUBLIC_URL: https://school.example.com
    volumes:
      - /data/assets:/data/assets
    depends_on: [postgres, redis]
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://localhost:3000/health"]
      interval: 15s
    <<: *logging

  postgres:
    image: postgres:17-alpine
    restart: unless-stopped
    cpuset: "6"
    shm_size: 1g
    command: >
      postgres -c shared_buffers=4GB -c effective_cache_size=12GB
               -c max_connections=200 -c wal_level=replica
               -c archive_mode=on -c archive_command='wal-g wal-push %p'
    volumes: ["/data/pg:/var/lib/postgresql/data"]
    <<: *logging

  redis:
    image: redis:7-alpine
    restart: unless-stopped
    cpuset: "6"
    command: redis-server --appendonly yes --maxmemory 2gb --maxmemory-policy noeviction
    volumes: ["/data/redis:/data"]
    networks: [default, convnet]
    <<: *logging

  livekit:
    image: livekit/livekit-server:latest
    restart: unless-stopped
    network_mode: host                 # ОБЯЗАТЕЛЬНО: UDP-диапазон
    cpuset: "0-3"                      # ЭКСКЛЮЗИВНО
    command: --config /etc/livekit.yaml
    volumes: ["./livekit.yaml:/etc/livekit.yaml:ro"]
    <<: *logging

  coturn:
    image: coturn/coturn:latest
    restart: unless-stopped
    network_mode: host
    cpuset: "0-3"
    volumes: ["./turnserver.conf:/etc/coturn/turnserver.conf:ro"]
    <<: *logging

  converter:                           # ИЗОЛИРОВАН
    build: ./services/converter
    restart: unless-stopped
    cpuset: "7"
    cpu_quota: 80000                   # 0.8 CPU
    mem_limit: 3g
    networks: [convnet]                # только redis, НЕТ выхода в интернет
    read_only: true
    security_opt: ["no-new-privileges:true"]
    cap_drop: ["ALL"]
    tmpfs: ["/tmp:size=2g"]
    volumes: ["/data/assets:/data/assets"]
    <<: *logging

networks:
  default:
  convnet:
    internal: true                     # ключевое: нет маршрута наружу

volumes:
  caddy_data:
```

> **Про изоляцию конвертера — реши однозначно на Этапе 3.** `network_mode: none` отрезает контейнер от сети целиком, включая Redis: общаться тогда можно только через общий том (файл-задание → файл-результат → файл-статус). Надёжнее всего, но неудобно.
>
> **Рекомендуемый компромисс:** отдельная внутренняя docker-сеть, где видны только `converter` и `redis`, без выхода в интернет:
>
> ```yaml
> networks:
>   convnet: { internal: true }     # internal: true = нет маршрута наружу
> services:
>   converter:
>     networks: [convnet]           # видит redis, не видит интернет
>     read_only: true
>     cap_drop: ["ALL"]
>     security_opt: ["no-new-privileges:true"]
>     tmpfs: ["/tmp:size=2g"]
>   redis:
>     networks: [default, convnet]
> ```
>
> Конвертер берёт задания из очереди BullMQ, читает и пишет в `/data/assets`, в интернет выйти не может. Именно эта конфигурация имеется в виду дальше по документу.

`Caddyfile` — почти весь конфиг:

```
school.example.com {
  encode zstd gzip
  handle /rtc/* {
    uri strip_prefix /rtc
    reverse_proxy localhost:7880
  }
  handle {
    reverse_proxy app:3000
  }
}
```

## Приложение В. Работа с Claude Code

Это ТЗ рассчитано на парную работу с Claude Code. Несколько практических правил:

- **`CLAUDE.md` в корне** с: стеком, соглашениями об именовании, структурой папок, правилом «никаких новых зависимостей без обсуждения», ссылкой на этот документ.
- **Один этап = одна ветка = один длинный контекст.** Не мешать «доску» и «видео» в одном чате.
- **Схемы Zod пиши первыми.** Claude Code хорошо генерирует код от типов и плохо — от прозы.
- **Тесты на движок проверки заданий — обязательно.** Это единственное место, где баг тихо портит оценки учеников. Claude Code отлично пишет табличные тесты по схеме.
- **WebRTC и Yjs — не делегируй слепо.** Здесь мало обучающих данных и много подводных камней; читай сгенерированный код внимательнее обычного.
- **Конвертер, миграции, воркеры, админка, CRUD** — делегируй смело, это 60% объёма кода и 15% сложности.
- **Правила модульности монолита (§4.1.1) — в `CLAUDE.md` дословно.** Иначе Claude Code через месяц свяжет модули напрямую, и швы для будущего распила исчезнут. Подкрепи `dependency-cruiser` в CI: правило важнее намерения.
- **`docker-compose.yml` и `deploy.sh` — не генерировать «примерно».** Это то, что ломает прод молча. Читай построчно.
