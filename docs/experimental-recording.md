# Экспериментальная запись уроков (raw-дорожки + журнал + отложенная сборка)

Статус: **прототип для сравнения с Egress**. Основная запись — по-прежнему
LiveKit Egress Room Composite (`recordings/service.ts`), метод по умолчанию.

## 1. Аудит (2026-10-12) — что есть в коде

Жизненный цикл текущей записи:

1. Учитель жмёт «Запись» → `POST /lessons/:id/recordings` →
   `startLessonRecording()` (права, `RECORDING_ENABLED`, настройка школы,
   «одна активная на урок») → `egress.startRoomRecording()` (Room Composite,
   шаблон `/egress`, recorder-токен в query) → строка `recordings`
   (`starting`) → WS `recording_status` (баннер согласия).
2. Статус едет вебхуками `egress_started/updated/ended` →
   `applyEgressWebhook()` → `applyEgressEvent()` (терминальный не
   откатывается, `ready` ставит длительность/размер/ретеншн, обложка ffmpeg).
3. Стоп: `POST …/stop` → `stopEgress` → `processing`, дальше вебхук.
4. Файл: `recordings/<school>/<lesson>/<id>.mp4` в `STORAGE_ROOT`, выдача
   только presigned `/files/...`; ретеншн — часовой свип.

Найденные дефекты основной записи:

- `reconcileRecording()` нигде не вызывается — потерянный вебхук оставляет
  запись в `starting/recording/processing` навсегда.
- Ошибка старта egress сразу 502 без повтора; при таймауте ответа egress мог
  всё же стартовать — строка не создаётся, файл пишется «в никуда».

Серверные точки, доступные для журнала (без новых клиентских соединений):

| Данные | Где на сервере |
|---|---|
| сцена, задания, presence, рука, закрепление, режим, демонстрация (claim) | `rooms/events.ts#emitRoomEvent` — все WS-сообщения урока, включая `activity_*` и `recording_status` из других модулей (`broadcastToLesson`) |
| состав LiveKit, публикация/снятие дорожек | вебхук `rooms/livekit-webhook.ts` (`participant_*`, `track_*`) |
| доска (Excalidraw в Y.Doc), страницы, PDF/слайды (страницы с `slide.imageUrl/pdfUrl`, TTL ссылок 30 дней) | Hocuspocus в процессе API (`canvas/hocuspocus.ts`): хук `onChange` (каждый Yjs-update), `onAwarenessUpdate` (viewport учителя) |
| вид задания в записи (без ключей и личных ответов) | `activities/service.ts#getRecorderView` |

Ограничения, проверенные по коду:

- Снимок доски в БД (`canvas_docs`) — только последнее состояние, дебаунс 3 с:
  для «состояния на момент t» нужен поток Yjs-updates, а не снимок.
- `RecorderActivityStage` опрашивает вид задания каждые 5 с — в записи
  прогресс класса и сейчас дискретен с шагом 5 с.
- Клиенты публикуют VP8 (simulcast) и Opus; демонстрация — VP8.

## 2. План изменений (минимальный безопасный срез)

Отдельно от новой архитектуры — **исправления основной записи**:
сверка зависших записей (`reconcileRecording` по таймеру), идемпотентный
повтор старта egress.

Новая архитектура — отдельный путь, своё состояние:

| Часть | Что |
|---|---|
| Выбор метода | таблица `lesson_recording_modes` (урок → `egress`/`experimental`/`both`) + env-допуск `RECORDING_EXPERIMENTAL_SCHOOL_IDS` + `RAW_RECORDER_SECRET`. Нет строки, школы нет в списке или пустой секрет → `egress` |
| Состояние | таблица `raw_recordings` (свои статусы, лизы, попытки, ошибки), не трогает `recordings` |
| Журнал | таблица `raw_recording_journal` (seq, серверное время, тип, payload/bytes); пишется только пока идёт экспериментальная запись урока |
| API | внутренние эндпоинты `/internal/raw-recorder/*` для рекордера и рендера (секрет), админские для режима урока, слияние в `GET /lessons/:id/recordings` |
| Рекордер | Go-сервис `services/raw-recorder` (`livekit/server-sdk-go`): скрытый участник, RTP как есть в 60-с чанки + время прихода + RTCP SR |
| Рендер | тот же бинарник, режим `render`: RTP → IVF/Ogg с выравниванием времени, кадры доски/задания через Chrome (страница `/recording-replay`, те же `Board` и вид задания), сборка ffmpeg, проверка ffprobe, атомарная публикация |
| Деплой | отдельный `docker-compose.raw-recorder.yml`, `deploy.sh` его не поднимает |

## 3. Как устроено

```
урок ──► LiveKit ──► rawrec record (скрытый участник RR_…, только подписка)
                       └─ RTP как есть + время прихода → raw-recordings/<школа>/<урок>/<id>/attempt-N/<дорожка>/chunk-*.rtpd
API ──► журнал урока (raw_recording_journal): WS-события, Yjs-updates, viewport, вид задания, вебхуки LiveKit
после стопа: rawrec render
  convert  → render/tracks/*.ivf|*.ogg + index.json (время RTP → часы хоста)
  journal  → состав, сцены, моменты изменений доски
  layout   → сегменты с постоянной раскладкой (как шаблон /egress)
  frames   → Chrome открывает /recording-replay, снимает PNG доски/задания
  segments → ffmpeg, H.264, одинаковые параметры
  audio    → все микрофоны на одну шкалу → AAC
  mux → verify (ffprobe + пробное декодирование) → rename в recordings/<школа>/<урок>/<id>.mp4
API: ready — только если файл на месте и размер совпал с отчётом рендера
```

**Общая шкала времени.** И журнал (API), и метки прихода RTP (рекордер) — часы
одного хоста (`CLOCK_REALTIME`). Для каждой дорожки время RTP переводится в часы
хоста по нижней огибающей «приход − время RTP»: минимум по окнам отсекает
сетевую задержку, линейная подгонка — дрейф часов отправителя, ступеньки
больше 50 мс (возврат из DTX, перезапуск захвата) делят дорожку на участки,
скачки больше 2 с — тоже. Если API и рекордер на разных хостах, нужна
синхронизация часов (chrony); погрешность часов прямо войдёт в сдвиг доски
относительно видео. Yjs и RTP сами по себе не синхронизированы — связь только
через это общее время хоста. RTCP Sender Report рекордер сохраняет, но не
использует (см. ограничения).

**Порядок и полнота журнала.** `seq` раздаёт процесс API в порядке
поступления; повтор пары (запись, seq) отбрасывается БД. Буфер сбрасывается
раз в 500 мс; после рестарта API журнал продолжается (`journal_started`,
`reason: resume`) с новым ключевым кадром доски. Раз в 10 с —
`journal_heartbeat`: по самой длинной паузе видна дыра. Раз в 5 минут —
ключевой кадр доски (`yjs_snapshot`).

**Статусы** (`raw_recordings.status`, отдельно от `recordings`):
`requested → recording → finalizing → queued_for_render → rendering →
verifying → ready`, ошибки — `failed` (с `last_error`), `aborted`, `deleted`.
В интерфейсе урока проецируются на шкалу основной записи (`starting`,
`recording`, `processing`, …) с пометкой «эксперимент».

## 4. Как включить только для тестового урока

1. В `.env` app (два уровня защиты от случайного включения):
   ```
   RAW_RECORDER_SECRET=<openssl rand -hex 32>
   RECORDING_EXPERIMENTAL_SCHOOL_IDS=<uuid школ через запятую | all>
   RAW_RECORDER_LIVEKIT_URL=ws://127.0.0.1:7880
   RAW_RENDER_REPLAY_ORIGIN=http://127.0.0.1:3000
   ```
   перезапуск app (`./deploy.sh`), миграция `0034` применится сама.
2. Рекордер и рендер (отдельный compose-проект, тот же секрет в `.env.raw-recorder`):
   ```
   docker compose -f docker-compose.raw-recorder.yml --env-file .env.raw-recorder up -d --build
   ```
3. Режим урока — только admin, только для школы из списка:
   ```
   PUT /api/v1/admin/lessons/<lessonId>/recording-mode  {"mode":"both"}         # оба метода, сравнение
   PUT /api/v1/admin/lessons/<lessonId>/recording-mode  {"mode":"experimental"} # только новый
   GET /api/v1/admin/lessons/<lessonId>/recording-mode                          # что применится
   ```
   Либо без режима урока: в диалоге «Начать запись урока?» кнопка
   **«Тестовая запись»** — запись этого запуска только экспериментальным
   методом (без Egress). Видна во всех школах из списка (`all` — во всех).
4. Учитель нажимает «Запись» как обычно. Состояние:
   `GET /api/v1/admin/raw-recordings/<id>` (статус, попытки, ошибка, метрики),
   пересборка упавшей: `POST /api/v1/admin/raw-recordings/<id>/retry-render`.

## 5. Возврат к Egress

- Один урок: `PUT …/recording-mode {"mode":"egress"}` (строка режима удаляется).
- Все уроки сразу: очистить `RECORDING_EXPERIMENTAL_SCHOOL_IDS` или
  `RAW_RECORDER_SECRET` в `.env` и перезапустить app — режимы уроков
  игнорируются, журнал и сверка не запускаются, внутренний API отвечает 404.
- Остановить воркеры: `docker compose -f docker-compose.raw-recorder.yml down`.
  Идущая экспериментальная запись без рекордера после стопа станет `aborted`;
  основная запись от этого не зависит ни в одном месте.
- Код основной записи не менялся, кроме двух исправлений (`a818d9c`): сверка
  зависших записей и повтор старта egress.

## 6. Хранение данных

| Что | Где | Сколько хранится |
|---|---|---|
| исходные дорожки (RTP + метки) | `raw-recordings/<школа>/<урок>/<id>/attempt-N/` | до `ready` — всегда; после `ready` — `RAW_RECORDING_SOURCE_RETENTION_HOURS` (по умолчанию 7 суток); после `failed` — 14 суток |
| рабочие файлы рендера | `…/<id>/render/` | удаляются с исходниками; сегменты — сразу после публикации |
| журнал урока | `raw_recording_journal` | удаляется вместе со строкой записи |
| готовый MP4 | `recordings/<школа>/<урок>/<id>.mp4` | как у Egress: `RECORDING_RETENTION_DAYS` |

Файлы пишет рекордер/рендер под uid 999 (как app) — API удаляет их по ретеншну.

## 7. Надёжность

- Рекордер: heartbeat каждые 5 с; нет 30 с — запись снова `requested`,
  следующий рекордер пишет новую попытку (`attempt-N+1`), рендер склеивает
  попытки по общей шкале. Перезапущенный воркер с тем же `WORKER_ID` забирает
  свои задания сразу (`/recover`), не дожидаясь 30 с.
- Потеря данных при падении рекордера — не больше несброшенного буфера (1 с) и
  времени до подключения новой попытки; чанки по 60 с, обрезанная последняя
  запись чанка читается до последней целой.
- API недоступен — рекордер продолжает писать (урок важнее отчёта).
- Рендер: лиза с heartbeat (3 мин), до 3 попыток, контрольные точки по шагам
  (конвертация, кадры, каждый сегмент, звук) — повтор продолжает с места.
- Дубли: условные UPDATE по лизе и статусу, `SKIP LOCKED` при взятии заданий,
  уникальный индекс «одна идущая на урок», (запись, seq) в журнале.
- Публикация: MP4 появляется под своим именем только через rename проверенного
  файла; API ставит `ready` после собственной проверки размера.
- Ошибка любого шага экспериментального метода не трогает строку Egress и
  не отменяет её запись (тесты `raw-service.test.ts`).

## 8. Ограничения и то, что пока прототип

- **Кодеки:** сборка поддерживает VP8 и Opus (так публикуют клиенты Матиса).
  Дорожки VP9/H.264/AV1 рекордер сохраняет, но в ролик они не попадут
  (`tracksUnsupported` в метриках).
- **Раскладка** повторяет шаблон `/egress` приближённо, средствами ffmpeg:
  плитки 16:9, имена через drawtext, лента 5 плиток плюс «ещё N», сетка по
  `fitGrid`. Индикаторы речи, поднятой руки, качества связи и аватары не
  рисуются. Доска и задание — те же React-компоненты (`Board`, лист
  задания) на странице `/recording-replay`.
- **Доска** снимается не чаще 2 кадров/с (`FRAME_STEP_MS`). Промежуточные
  штрихи в пределах 0,5 с в записи сливаются в один кадр.
- **Вид задания** пишется в журнал раз в 5 с, как шаблон Egress и опрашивает.
- **Камеры** записываются средним слоем simulcast (≈360p), демонстрация —
  верхним. Это настройки задания (`cameraQuality`/`screenQuality`).
- **Синхронизация** опирается на часы хоста. RTCP Sender Report сохраняется,
  но не используется; сверка с SR — следующий шаг.
- **Переподключение** участника — это новая дорожка. При падении рекордера
  теряется промежуток до подключения новой попытки (замер: 5,8 с при паузе
  перезапуска 5 с) плюс несброшенная 1 с.
- **Сборка по CPU пока не дешевле Egress** (см. §9): тяжёлая работа
  переносится из урока на потом, но её объём сопоставим. Возможные
  оптимизации (не сделаны): `preset faster/medium` по загрузке, 24 кадр/с,
  повторное использование неизменных кусков, аппаратное кодирование (Quick
  Sync на сервере выключен драйвером).
- **Safari** не проверялся вживую (на сервере его нет). Файл в формате,
  который Safari поддерживает: H.264 High 3.1 yuv420p, `avc1`, AAC-LC,
  `moov` в начале. В Chromium (Google Chrome из образа egress) проверено
  воспроизведение с начала и с середины без ошибок и потерь кадров.
- Метод проверен на **малых уроках** (1–4 участника). Урок на 30 человек,
  несколько уроков сразу и 50 одновременных записей не испытывались.

## 9. Испытания (стенд, 2026-10-12)

Стенд: отдельный app (сборка из рабочего дерева) со своими Postgres и Redis
на 127.0.0.1:3100. С продом общие только LiveKit и egress. Вебхуки LiveKit
на стенд не приходят, поэтому статус Egress там обновляла сверка (§2).
Нагрузка — генератор `/root/loadtest/gen` и сценарий доски.

**Сценарии.**

1. Оба метода (`both`), 229 с: учитель и 2 ученика с камерами и
   микрофонами. Ученик принудительно отключён (`kill -9`) на 52-й секунде,
   на 67-й вошёл новый. Доска: 2 страницы, viewport, смена сцен.
   Демонстрация экрана 1080p на 80–120-й секунде.
2. «Хлопушка», оба метода, 360 с: учитель один, вспышка и писк 1 кГц
   одновременно каждые 5 с. Старт петель звука и видео у отправителя
   зафиксирован в логе генератора.
3. Устойчивость, `experimental`, 229 с:
   - рекордер убит `kill -9` на 60-й секунде и через 5 с запущен снова;
   - на 100-й секунде перезапущен API;
   - во время сборки убит рендер.
4. Полный сценарий с заданием, `experimental`, 229 с.

**Ресурсы во время урока** (cgroup, CPU-секунды за окно урока, сценарии 1 и 2):

| | Egress | Рекордер |
|---|---|---|
| Сценарий 1 (229 с) | 184 CPU-с = 0,80 ядра, память до 782 МБ | 4,7 CPU-с = 0,02 ядра, до 86 МБ (с файловым кешем) |
| Сценарий 2 (360 с) | 179 CPU-с = 0,50 ядра, до 729 МБ | 2,6 CPU-с = 0,01 ядра, до 17 МБ |

**После урока** (финальная версия сборки):

| Запись | Длит. | Исходники | MP4 | Сборка (время / CPU) |
|---|---|---|---|---|
| сц. 1 | 228,7 с | 66 МБ (≈1,0 ГБ/ч) | 39,6 МБ | 103 с / 188 CPU-с |
| сц. 2 | 359,3 с | 1,7 МБ | 1,4 МБ | 125 с / 189 CPU-с |
| сц. 3 | 229,3 с | 52 МБ | 48,6 МБ | 86 с / 169 CPU-с |
| сц. 4 | 229,3 с | 68 МБ | 38,3 МБ | 95 с / 178 CPU-с |

Egress в сценарии 1: 84,7 МБ (3,0 Мбит/с, 226,8 с). Новый метод кодирует с
CRF 23 и потолком битрейта школы, поэтому файлы меньше. Качество попарно не
сравнивалось.

**Полнота медиа:**
- в сценариях 1, 3 и 4 рекордер потерял 0 пакетов (по номерам RTP);
- запросов ключевого кадра 4–6 за урок;
- выброшены служебные кадры SFU: 8×8 при смене слоя и «пустой» хвост
  дорожки отключившегося участника.

**A/V-синхронизация** («хлопушка», 71 пара):

| | вспышка − писк, среднее | разброс | дрейф |
|---|---|---|---|
| Egress | −117 мс | от −758 (первые секунды) до −70 мс | +7 мс/мин |
| Экспериментальный | −55 мс | от −7 (начало) до −112 мс (конец) | −19,5 мс/мин |

Дрейф экспериментальной записи уже есть в моментах прихода пакетов на
сервер. Генератор отправляет звук на −222 ppm, а видео на +267 ppm
относительно часов сервера: запись честно повторяет отправителя. У настоящих
браузеров захват идёт в реальном времени, но проверено это только на
генераторе.

**Устойчивость (сценарий 3):**
- **Падение рекордера.** Рекордер при старте вернул задание через
  `/recover`: попытка 2, без ожидания 30-секундной лизы. Дыра в медиа 5,8 с.
- **Рестарт API.** Журнал продолжился записью `journal_started`
  (`reason: resume`) с новым ключевым кадром доски. Номера событий 1…30
  идут без дыр и повторов.
- **Падение рендера.** Задание вернулось через `/recover` за ~3 с, готовые
  сегменты сохранились.
- **Негодный файл.** Сборка падала из-за ошибки ffmpeg (её исправление ниже).
  После трёх попыток запись честно получила `failed`, файл не опубликован,
  основная запись не затронута. Ручной `retry-render` после исправления
  собрал запись в `ready`.
- **Проверка перед публикацией** (интеграционный тест на ffmpeg)
  отбраковывает обрезанный файл, файл с испорченной серединой, файл без звука,
  неверную длительность и неверный размер.

**Дефекты, найденные испытаниями и исправленные:**
1. Ступеньки времени RTP при выходе из DTX (+380 мс) копились, и звук
   учеников уезжал на ~2,3 с. Исправление — деление дорожки на участки по
   устойчивым ступенькам нижней огибающей; медиана теперь 0,6 мс.
2. «Пустые» кадры LiveKit после падения участника с продолжением старых
   меток. Время теперь считается для каждого пакета по его участку, хвост
   отбрасывается.
3. ffmpeg сдвигал каждый вход к нулю, и звук отставал на ~850 мс.
   Исправление — `-copyts`.
4. Смена слоя simulcast перестраивала граф ffmpeg, и видео опережало на
   ~300 мс. Исправление — `-reinit_filter 0`. Кадры 8×8 и смена пропорций
   (граница сегмента) больше не роняют ffmpeg.

## 11. Нагрузочные испытания (2026-10-12, вечер)

### 11.1 Аудит и что реально доступно

- **Очередь сборки.** Строки `raw_recordings` в `queued_for_render`; взятие —
  `FOR UPDATE SKIP LOCKED`, с этого дня по возрасту (`queued_at`, миграция
  0035, ставит триггер). Лиза рендера 3 мин, heartbeat 30 с, до 3 попыток.
  Перезапущенный воркер сразу возвращает свои задания (`/recover`).
- **Воркеры.** Один контейнер рендера = один воркер = одна запись за раз;
  внутри записи параллельны сегменты (`RENDER_PARALLEL`), длинные сегменты
  можно резать (`MAX_SEGMENT_SEC`, добавлено сегодня). Рекордер — один
  процесс на много записей (`RAW_RECORDER_MAX_JOBS`, по умолчанию 10: для
  50 уроков нужно поднять или запустить несколько рекордеров).
- **Метрики очереди** (добавлены): `raw_recording_jobs{status}`,
  `raw_render_oldest_age_seconds`, `raw_render_backlog_lesson_seconds`.
- **Железо — один хост:** 6 ядер / 12 потоков, 31 ГБ ОЗУ, 1 Гбит/с, 370 ГБ
  свободно. LiveKit — продовый (ядра 1,2,7,8). Под запись и сборку — только
  ядра 4,5,10,11 (их же делит прод-egress). Генераторы участников — на ядрах
  ОС и app (0,6,3,9), как в прошлых нагрузочных тестах.
- **Ограничение.** 50 полных уроков по 30 человек требуют по прошлым замерам
  ~16 ядер LiveKit и ~4 Гбит/с — на этом хосте невозможно и опасно для
  прода. Поэтому этап A — 50 одновременных **малых** уроков (учитель +
  ученик); масштаб LiveKit для полных уроков — расчёт, не замер.
- **Безопасность.** Стенд (свой app, Postgres, Redis); сторож останавливает
  нагрузку при живом уроке на проде, задержке прод-API > 1 с или LiveKit
  > 2 ядер; рендер-воркеры встают на паузу при уроке или egress на проде.
  Сторож дважды сработал на проверках владельца — тест прерывался, прод не
  пострадал.

### 11.3 Этап B — скорость сборки (измерено)

Под сборку на этом хосте — 4 потока (ядра 4,5,10,11). x264 `veryfast`,
720p, кадр/с школы стенда 30.

**Пропускная способность пула** на одной очереди (105 трёхминутных уроков из
этапа A, учитель + ученик), окна по 11–18 мин:

| Пул (воркеры × сегменты, CPU на воркер) | Записей/ч | Часов урока / ч | Сборка одной, p50 | Загрузка ядер | CPU-с на с урока |
|---|---|---|---|---|---|
| 1 × 4, 4 CPU | 75 | 3,8 | 45 с | 2,7 из 4 | 0,68 |
| 2 × 2, 2 CPU | 104 | 5,2 | 72 с | 3,7 из 4 | 0,74 |
| 4 × 1, 1 CPU | 108 | 5,4 | 139 с | 3,9 из 4 | 0,75 |

Один воркер не загружает 4 ядра: конвертация, кадры доски, звук и склейка
последовательны. 2 × 2 — почти максимум пропускной способности при вдвое
меньшем времени одной сборки, чем 4 × 1.

**Часовой урок** (4 участника, 10 мин демонстрации, доска 94 кадра, 6
заданий; 40 сегментов при `MAX_SEGMENT_SEC=120`), один воркер на 4 CPU:

параллельно), конвертация 5 с, кадры доски 15 с, проверка 0,5 с. MP4 1,05 ГБ
(генератор шлёт «тяжёлое» видео — полосы и градиенты; у живых камер меньше).

### 11.5 Этап D — что ограничивает сборку (измерено)

- **CPU.** Сборка упирается в процессор: диск — до 27 МБ/с записи, память
  воркера — сотни МБ, сеть не участвует. Один воркер не загружает свои ядра
  из-за последовательных шагов → несколько воркеров эффективнее (§11.3).
- **Один большой урок не блокирует остальных** при ≥2 воркерах; при одном
  воркере часовой урок занимает его на 17 мин.
- **Падение воркера:** задание возвращается через `/recover` (при том же
  `WORKER_ID`) или по лизе за 3 мин; повторов сборки одного урока
  параллельно не было (лиза, `SKIP LOCKED`).
- **Стоимость кодирования** (3-минутная запись, CPU-с на секунду урока):
  veryfast 30 к/с — 0,70; veryfast 24 к/с — 0,61; superfast 30 — 0,50;
  superfast 24 — 0,44 (файл +61 %); faster 24 — 0,82.
- **Улучшения по итогам:** звук сводится параллельно с видео (−85 с на
  часовом уроке), очередь по возрасту (`queued_at`), метрики очереди,
  нарезка длинных сегментов, пресет через `RENDER_X264_PRESET`.

### 11.8 Расчёт мощности (из замеров; это расчёт, не испытание)

Исходные замеры: сборка урока «учитель + ученик» — 0,70 CPU-с на секунду
урока (veryfast, 30 к/с), 0,61 при 24 к/с; часовой урок «4 участника +
демонстрация + доска» — 1,03 CPU-с/с (3762 CPU-с), одна сборка на 4 ядрах
17,4 мин; пул 2 × 2 использует 92 % ядер. Урок на 30 учеников со всеми
камерами не измерялся: в сетке «люди» видно до ~12 плиток, стоимость
выше — ниже взята 1,03 как нижняя граница.

| Вопрос | Расчёт |
|---|---|
| Часов урока в час на одно ядро (без роста очереди) | 0,92 / 1,03 ≈ **0,9** (4 участника), 0,92 / 0,70 ≈ 1,3 (2 участника) |
| Этот хост (4 потока под сборку) | ≈3,6 часа урока в час (4 участника), 5,2 — измерено для 2 участников |
| 50 часовых уроков в час, равномерно | 50 × 3762 CPU-с / 3600 с ≈ 52 ядра при 100 % → ≈57 при 92 % → **≈95 ядер** при загрузке 60 % (ожидание мало) |
| Готовность ≤ 10 мин для одного часового урока | ≥ 3762 / 570 ≈ 6,6 рабочих ядра на сборку → воркер на **8 ядер** (`RENDER_PARALLEL=8`, `MAX_SEGMENT_SEC=120`), ≈9 мин |
| То же для потока 50/ч | 50 × 9 мин / 60 = 7,5 воркера заняты; при загрузке 60 % — 13 воркеров × 8 ядер + 1 запасной ≈ **110 ядер** |
| 50 уроков кончаются одновременно (одно расписание) | 188 000 CPU-с: при 110 ядрах последний готов через ≈31 мин (p95 ≈ 30 мин); p95 ≤ 10 мин потребовало бы ≈340 ядер — неэкономно |
| Дешевле на 37 % CPU | superfast + 24 к/с (0,44 CPU-с/с), но файл +61 % — дороже хранение |

**Исходные дорожки.** Замер: ≈0,23 ГБ/ч на участника (камера средним слоем
+ микрофон); часовой урок 4 участников с демонстрацией — 1,1 ГБ. Расчёт для
класса 31 человека со всеми камерами: ≈7 ГБ/ч на урок, 50 уроков —
≈350 ГБ/ч и ≈100 МБ/с записи — на текущем диске (370 ГБ свободно) место
кончится за час. Обязательно до полных уроков: камеры учеников писать
нижним слоем (в 3–4 раза меньше), исходники удалять через сутки после
`ready` (`RAW_RECORDING_SOURCE_RETENTION_HOURS=24`).

**LiveKit для полных уроков** (из прошлого отчёта о мощности): ≈0,32 ядра и
≈80 Мбит/с исходящего на урок из 31 человека → 50 уроков ≈16 ядер и ≈4 Гбит/с
— нужен кластер LiveKit; рекордер тут ни при чём (0,31 ядра на 50 записей).

### 11.9 Ответы на вопросы задания

1. **50 одновременных записей.** Рекордер — да, измерено на 50 малых уроках
   (0,31 ядра, 270 МБ, 0 потерь). 50 полных классов этот сервер не
   выдержит из-за LiveKit/сети (расчёт ≈16 ядер, ≈4 Гбит/с) и сборки (CPU).
2. **Один воркер, часовой урок:** 17,4 мин на 4 ядрах, 3762 CPU-с
   (4 участника, демонстрация, доска). Полный класс не измерен.
3. **Воркеров для 50 уроков:** ≈13 воркеров по 8 ядер + 1 запасной
   (≈110 ядер) при равномерном окончании уроков — расчёт (§11.8).
4. **Уроков в час без роста очереди:** этот хост — ≈3,6 часа урока в час
   (4 участника) / 5,2 (2 участника, измерено); на ядро ≈0,9 часа урока/ч.
5. **Максимум готовности:** нормальный поток 68 с, волны 75 % — 7,7 мин,
   пик 15,2 мин, перегрузка 18,6 мин, разовый всплеск 105 записей — 78 мин
   (трёхминутные уроки, пул 2 × 2).
6. **p95 ≤ 10 мин:** да для коротких уроков при нагрузке ≤ 75 % (p95 7,7
   мин); нет при пике (14,4 мин) и перегрузке (18,1 мин); для часового урока
   на этом хосте нет даже без очереди (17,4 мин) — нужно 8 ядер на воркер.
7. **Очистка после всплеска:** 26 заданий — 21 мин, 32 — 26 мин (поток
   продолжал поступать), 105 — 85 мин.
8. **Влияние сборки на уроки:** не обнаружено (потери 0, джиттер < 1 мс,
   замираний 0, LiveKit и прод-API без изменений) — сборка на своих ядрах.
9. **Ограничения:** CPU сборки (главное), LiveKit и сеть для полных
   классов, диск под исходники полных классов (≈350 ГБ/ч на 50 уроков),
   только 4 потока под сборку на этом сервере.
10. **Нужно:** отдельные серверы сборки (≈110 ядер на 50 часовых уроков в
    час с готовностью ≈9 мин; при одновременном окончании — p95 ≈30 мин),
    кластер LiveKit, камеры учеников нижним слоем, ретеншн исходников 24 ч,
    выбор пресета/кадр/с (superfast + 24 к/с −37 % CPU, файл +61 %).
