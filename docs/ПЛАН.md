# План разработки для Claude Code

**Спутник документа:** `ТЗ_видеоплатформа_онлайн-школа.md` (v1.3)
**Формат:** исполняемый роадмап. Каждый этап — набор сессий с Claude Code, стоп-лист и нагрузочный гейт.
**Принцип очерёдности:** сначала то, что дёшево для сервера и держит нагрузку; дорогое — потом.

---

## 0. Принцип: порядок по стоимости нагрузки, а не по «интересности»

Обычный порядок разработки видеоплатформы — «сначала видео, потом всё остальное». Он неверен для соло-разработчика на одной машине по двум причинам:

1. **Видео — самый дорогой класс нагрузки и самый шумный при отладке.** Пока в комнате летит 300 Мбит/с, невозможно понять, из-за чего подвисает доска: из-за твоего кода или из-за забитого канала.
2. **Видео не является ядром урока.** Урок с голосом, общей доской и слайдами — это полноценный урок. Видео учеников — комфорт, а не функция.

Поэтому порядок такой: **каждый этап добавляет ровно один новый класс нагрузки, и между этапами стоит гейт.** Не прошёл гейт — не идёшь дальше. Это единственный способ понять, какой именно этап сломал производительность.

### Карта нагрузки

| Этап | Что добавляет | Трафик на 10 уроков | CPU | RAM | Ключевой риск |
|---|---|---|---|---|---|
| **Э0** Скелет | HTTP, БД | ~0 | ~0 | 0,5 ГБ | нет |
| **Э1** Комната | WebSocket, presence | < 1 Мбит/с | ~0 | +0,5 ГБ | утечка соединений |
| **Э2** Аудио | Opus, SFU | **~30 Мбит/с** | 10–20% | +0,2 ГБ | эхо, устройства |
| **Э3** Доска | Yjs в памяти | < 2 Мбит/с | 5% | **+1–2 ГБ** | утечка Y.Doc |
| **Э4** Слайды | разовые CPU-вспышки | ~0 в уроке | **всплеск 80%** | +0,5 ГБ | конвертер рвёт аудио |
| **Э5** Видео учителя | 1 паблишер × N | **~300 Мбит/с** | 30% | — | канал |
| **Э6** Видео учеников | 9 паблишеров × N | **~700 Мбит/с** | 50–70% | — | **потолок платформы** |
| **Э7** Демо экрана | 1 паблишер, 1080p | +50 Мбит/с | +5% | — | fps vs читаемость |
| **Э8** Задания | HTTP, WS | +2 Мбит/с | ~0 | +0,3 ГБ | нет |
| **Э9** Редактор | ничего | ~0 | ~0 | ~0 | нет (объём кода) |
| **Э10** Запись | Chrome + кодирование | — | **2–6 ядер** | +4 ГБ | **вторая машина** |

Обрати внимание на строки Э5 и Э6: **две трети всей нагрузки платформы добавляются на двух этапах из одиннадцати.** До них система работает почти даром. Это и есть причина порядка.

### Что меняется по сравнению с §12 ТЗ

В ТЗ этапы шли по продуктовой логике (видео → доска → слайды). Здесь они переставлены по нагрузке. Практические следствия:

- **Первый реальный урок можно провести на 3-м месяце, а не на 4-м** — аудио + доска + слайды готовы раньше, потому что видео не тянет за собой отладку канала.
- **Видео учителя добавляется за полторы недели**, а не за месяц: инфраструктура LiveKit, права, сетка участников, проверка устройств — всё уже сделано на Э2.
- **Потолок платформы измеряется на Э6, когда всё остальное уже стабильно.** Если 4 класса по 30 не влезают — это ограничение продукта, а не баг в коде, и ты это точно знаешь.

**Честная оговорка.** Учителям идея «пилот без видео» может не понравиться. Если школа настаивает — пилот начинается после Э5 (видео учителя), это всего плюс полторы недели. Но **не после Э6**: видео учеников можно включать, только когда урок уже отработан.

## 1. Правила работы с Claude Code

Эти правила важнее самих задач. Без них план развалится на третьем этапе.

### 1.1 Один этап = один контекст

Не смешивать этапы в одной сессии. Начиная новый этап — новый чат, и первым сообщением идёт промпт из раздела этапа.

### 1.2 `CLAUDE.md` в корне — обязателен

Он читается автоматически и держит рамки. Минимальное содержимое:

```markdown
# Контекст проекта
Видеоплатформа для одной онлайн-школы. Монолит на одном сервере.
Спецификация: ./docs/ТЗ.md — читай перед архитектурными решениями.
План: ./docs/ПЛАН.md — текущий этап указан в ./docs/CURRENT_STAGE.md

# Стек (не менять без обсуждения)
Node 22 + Fastify + TypeScript + Drizzle + PostgreSQL 17 + Redis 7
React 19 + Vite + Tailwind + Zustand
LiveKit (self-hosted), Yjs + Hocuspocus, Excalidraw

# Железные правила
- НЕ добавлять зависимости без явного разрешения. Предложить и дождаться ответа.
- НЕ использовать localStorage/sessionStorage.
- Модуль экспортирует только service.ts. Никто не импортирует чужой repo.ts.
- Все внешние адреса — через env. Ни одного захардкоженного localhost.
- Доступ к файлам — только через StorageAdapter.
- Схемы Zod живут в packages/shared и используются и фронтом, и бэком.
- Ничего с чужих CDN. Шрифты, KaTeX, иконки — в бандле.
- Ключи ответов на задания никогда не уходят на клиент до сабмита.

# Как работать
- Сначала Zod-схема и типы, потом реализация.
- Каждая задача заканчивается зелёными тестами и рабочим `docker compose up`.
- Если задача выходит за рамки текущего этапа — остановись и скажи об этом.
```

### 1.3 Стоп-лист сильнее списка задач

Главный режим отказа Claude Code — «сделать заодно и соседнее». Пишешь доску — он захочет добавить экспорт в PDF. Пишешь аудио — предложит видео. **В каждом этапе ниже есть стоп-лист. Копируй его в промпт дословно.**

### 1.4 Что не делегировать вслепую

| Делегируй смело | Читай построчно |
|---|---|
| CRUD, миграции, формы, админка | Всё, что касается WebRTC и конфигов LiveKit |
| Конвертер, воркеры, очереди | Логика прав доступа и выдачи токенов |
| Компоненты UI, вёрстка | Движок проверки заданий (тихо портит оценки) |
| Тесты по готовым схемам | `docker-compose.yml`, `deploy.sh`, `Caddyfile` |
| Рефакторинг внутри модуля | Работа с Y.Doc: жизненный цикл, освобождение памяти |

### 1.5 Definition of Done для любой задачи

1. Код собирается: `pnpm build` без ошибок и без `any`.
2. Тесты зелёные: `pnpm test`.
3. `docker compose up` поднимается с нуля на чистом окружении.
4. Фича проверена руками в браузере.
5. Нет новых зависимостей, кроме согласованных.
6. `dependency-cruiser` не ругается на связи модулей.

### 1.6 Ритм

Одна задача = одна сессия = один коммит. Задача, которая не влезает в сессию, разбита неправильно — дроби дальше.

### 1.7 MCP-серверы: подключать по этапам, а не всё сразу

MCP даёт Claude Code прямой доступ к БД, браузеру, метрикам и репозиторию — вместо того, чтобы ты копировал вывод команд в чат руками. Но у него есть цена, о которой обычно не пишут.

**Три причины не включать всё сразу:**

1. **Токены.** Каждый подключённый сервер вливает в контекст определения своих инструментов — обычно 2 000+ токенов, а у серверов с большой схемой БД бывает и 6 000+. По замерам Scalekit, вызов через MCP обходится в 10–32 раза дороже по токенам, чем эквивалентная команда в терминале. Пять серверов съедают контекст ещё до первого твоего слова.
2. **Внимание модели.** Чем больше инструментов, тем чаще Claude Code выбирает не тот.
3. **Безопасность.** В апреле 2026 OX Security раскрыла системную RCE-уязвимость во всех языковых реализациях MCP SDK. Держи SDK обновлёнными и не давай серверам больше прав, чем нужно.

**Правило: 3 постоянных + 1–2 под текущий этап. Больше пяти одновременно — не подключать.**

#### Постоянный набор (весь проект)

| Сервер | Кто | Зачем именно здесь |
|---|---|---|
| **Context7** | Upstash | Актуальная документация библиотек прямо в контекст. **Самый ценный для этого проекта:** LiveKit, Yjs, Hocuspocus и Excalidraw активно меняют API, и модель уверенно галлюцинирует методы двухлетней давности. Context7 это лечит |
| **Playwright MCP** | Microsoft | Браузерная автоматизация, 22 инструмента, ~30k звёзд. Работает через accessibility-снимки страницы, а не скриншоты — поэтому понимает структуру, а не картинку. Для нас критично: **два браузерных контекста одновременно = учитель и ученик в одном уроке** |
| **GitHub MCP** | GitHub | Issues, PR, статусы Actions. Для соло-разработчика польза средняя, но сервер дешёвый |

#### Ситуативные

| Сервер | Кто | Когда включать |
|---|---|---|
| **Postgres MCP Pro** (`crystaldba/postgres-mcp`, MIT) | сообщество | Э0, Э3, Э8. Не только SQL: EXPLAIN с гипотетическими индексами, топ медленных запросов из `pg_stat_statements`, анализ нагрузки с рекомендацией индексов, health checks |
| **Grafana MCP** | Grafana Labs | Э4–Э7, Э10. Читает Prometheus и дашборды. **Именно этим закрываются нагрузочные гейты:** можно попросить сравнить джиттер аудио до и после конвертации PPTX, а не листать графики глазами |
| **Chrome DevTools MCP** | Google | Э2–Э7, Э9. Консоль, сетевая диагностика, performance-трейсы. Плюс проверка автономности: «покажи все запросы на чужие домены» |
| **Redis MCP** | сообщество | Э1. Инспекция ключей presence и TTL. Через неделю после Э1 отключить |
| **Figma MCP** | Figma | Э9, если UI редактора рисуется в Figma |

#### Чего НЕ ставить

- **Референсные серверы Anthropic образца 2024 года.** В 2025-м 13 из 20 были заархивированы, включая оригинальный Postgres. Половина туториалов в сети ведёт на мёртвый код. Для Postgres — только `crystaldba/postgres-mcp`.
- **Filesystem MCP.** У Claude Code и так есть доступ к файловой системе проекта.
- **Sentry MCP** — он ходит в API Sentry, а у нас GlitchTip. Совместимость там на уровне протокола SDK, а не API. Проверить можно, рассчитывать — нет.
- **Kubernetes, Cloudflare, Supabase, Stripe** — ничего из этого в проекте нет.

#### Безопасность подключений

```
1. Postgres MCP на прод — ТОЛЬКО --access-mode=restricted (read-only),
   и отдельным пользователем БД:
     CREATE USER mcp_ro WITH PASSWORD '...';
     GRANT CONNECT ON DATABASE school TO mcp_ro;
     GRANT USAGE ON SCHEMA public TO mcp_ro;
     GRANT SELECT ON ALL TABLES IN SCHEMA public TO mcp_ro;
2. Write-доступ — только к локальной dev-БД. Никогда к проду.
3. Playwright и Chrome DevTools — на localhost и staging.
   На прод натравливать только вручную и осознанно.
4. Никакого доступа MCP к .env и файлам с секретами.
5. Обновлять MCP SDK: RCE-уязвимость апреля 2026.
6. В CLAUDE.md прописать намерение, а не только доступ:
   "Postgres MCP — для вопросов о данных и планов запросов.
    НИКОГДА не изменяй данные на проде."
```

#### Что MCP не заменяет

Нагрузочные тесты — это `livekit-cli load-test`, `k6`, `autocannon` из терминала. MCP тут не нужен и только сожжёт токены. **MCP полезен для интерпретации результата** (Grafana MCP: «сравни CPU и трафик за окно теста»), а не для его запуска.

То же с `docker stats`, `docker compose logs`, `restic` — обычный bash быстрее и дешевле.

#### Базовый `.mcp.json`

```jsonc
{
  "mcpServers": {
    "context7":   { "command": "npx", "args": ["-y", "@upstash/context7-mcp"] },
    "playwright": { "command": "npx", "args": ["-y", "@playwright/mcp@latest"] },
    "github":     { "command": "npx", "args": ["-y", "@modelcontextprotocol/server-github"],
                    "env": { "GITHUB_PERSONAL_ACCESS_TOKEN": "${GITHUB_TOKEN}" } }
    // ситуативные добавляются и удаляются по этапам — см. пометки MCP в каждом этапе
  }
}
```

## Э1 — Комната без медиа · 1,5 недели

**Добавляет нагрузки:** WebSocket-соединения, presence. < 1 Мбит/с на 10 уроков.
**Почему сейчас:** WebSocket-слой понесёт на себе всё остальное — доску, задания, команды учителя. Отладить его в тишине, без медиатрафика, стоит полутора недель и экономит потом неделю догадок.

**В конце этапа работает:** учитель и ученики заходят в урок, видят список участников, пишут в чат, поднимают руку. Учитель выдаёт и отбирает права. Звука нет.

> **MCP:** постоянный + **Redis MCP** (временно) + Postgres MCP.
> Ключевой приём этапа: **Playwright с двумя браузерными контекстами** — один учитель, один ученик, оба в одном уроке. Так проверяется всё: presence, чат, выдача прав, реконнект. Сценарий «учитель забрал право у ученика → у ученика поменялся UI» автоматизируется целиком.
> Redis MCP — посмотреть ключи presence и TTL при отладке Э1.2. **Через неделю отключить**, дальше он не нужен.

## Э8 — Движок заданий: плеер · 6 недель

**Добавляет нагрузки:** практически ничего. HTTP + WS.
**Почему после видео:** дёшево для сервера, но объёмно по коду. Пока делаешь эти шесть недель, платформа уже работает на пилоте и приносит пользу.

**В конце этапа работает:** учитель выдаёт классу задание, видит живой прогресс, получает автопроверенные результаты.

> **MCP:** постоянный + **Postgres MCP Pro**. Grafana можно отключить — нагрузки здесь нет.
> - **Postgres MCP Pro раскрывается именно тут.** Таблица `responses` растёт быстрее всех, а аналитика по вопросам — это агрегаты. Инструменты «топ медленных запросов» и «анализ нагрузки с рекомендацией индексов» дают готовый ответ вместо угадывания. EXPLAIN с гипотетическими индексами позволяет проверить индекс до того, как его создавать.

> - **Что делать вручную:** движок проверки (Э8.3) читать построчно. Это единственное место, где баг тихо портит оценки учеников, и никакой MCP этого не поймает.

### Где MCP реально экономит время в этом проекте

Четыре места, где отдача очевидна:

1. **Playwright с двумя контекстами (Э1, Э3).** Урок — это всегда минимум два человека. Ручная проверка «открой два браузера, зайди под разными, порисуй» повторяется десятки раз за этап. Автоматизируется один раз и работает до конца проекта.
2. **Context7 на LiveKit, Yjs и Excalidraw (Э2, Э3).** Три библиотеки с подвижным API и устаревшими примерами в сети. Без Context7 модель уверенно пишет код двухлетней давности, и час уходит на непонятную ошибку.
3. **Grafana MCP на гейтах (Э4–Э6).** Гейты — это сравнение метрик «до и после». Глазами по графикам это долго и ненадёжно; запросом — минута.
4. **Postgres MCP Pro на Э8.** Таблица `responses` растёт быстрее всех, аналитика по вопросам — это агрегаты. Рекомендация индексов по реальной нагрузке лучше догадок.

### Где MCP не поможет

- **Нагрузочные тесты** — `livekit-cli load-test`, `k6`. Терминал.
- **`docker stats`, логи, `restic`** — bash быстрее и дешевле по токенам.
- **Движок проверки заданий (Э8.3)** — читать построчно самому. Единственное место, где баг тихо портит оценки учеников.
- **Конфиги LiveKit, `docker-compose.yml`, `deploy.sh`** — тоже вручную. MCP видит результат, но не понимает последствий неверного UDP-диапазона.
