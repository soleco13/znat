# Matís (matis-edu.ru): нагрузочные испытания и вместимость сервера

Дата: 2026-10-11. Сервер 95.213.143.106. Сырые данные — `reports/capacity-raw/`
(сводки ступеней `*/analysis.json`, клиенты `*/clients.jsonl`, монитор
`monitor.jsonl.gz`, исходное состояние `baseline.txt`).

## 1. Краткий вывод

* **Узкое место — запись уроков**, а не LiveKit, сеть или приложение. Одна
  запись урока (720p30, режим Room Composite — headless Chrome + H.264) стоит
  **1,5–1,7 CPU** и ~1,75 ГБ RAM. Под запись выделено 2 физических ядра
  (CPU 4,5,10,11) — на них помещается **2 одновременные записи**, третья не
  стартует.
* **Без записи** медиачасть выдержала **6 уроков × 31 участник = 186
  пользователей** (камеры, микрофоны, демонстрация экрана): LiveKit 48 % своих
  ядер, весь сервер 43 % CPU, потерь 0. Дальше не нагружали (решение
  остановить тесты), предел не достигнут.
* **Рекомендация на текущей конфигурации, если записывается КАЖДЫЙ урок:
  2 урока по 30 учеников, всего 62 пользователя** (подтверждено измерением,
  10 мин). При 720p30 egress загружен на 76 % (выше ориентира 70 %, но без
  потерь кадров); при 720p15 — 65 %.
* **Если записывается не каждый урок:** до 6 одновременных уроков по 30
  учеников (186 пользователей), из них записываются не более 2.
* **50 одновременных записей** на одной такой машине недостижимы: это ~80 CPU
  и ~90 ГБ RAM только на запись (расчётная оценка по измеренной цене одной
  записи). Пути — в разделе 12.

## 3. Методика

**Генератор нагрузки** — собственный клиент на Go (`livekit/server-sdk-go`
2.19, лежит в `/root/loadtest/gen`, вне репозитория — новые зависимости без
согласования в проект не добавлялись). Каждый синтетический участник идёт тем
же путём, что браузер: гостевой вход по ссылке / логин учителя → `POST /join`
→ WebSocket урока (присутствие, без него запись не видит участника) → LiveKit.

Публикация — заранее закодированные потоки с параметрами Matís (без
перекодирования, из памяти):

| Поток | Слои (simulcast) | Факт битрейта |
|---|---|---|
| Камера учителя | 720p24 / 360p / 180p | 1,70 / 0,51 / 0,23 Мбит/с |
| Камера ученика | 360p20 / 180p20 | 0,47 / 0,18 Мбит/с |
| Демонстрация экрана | 1080p15 / 720p15 / 360p5 | 2,17 / 0,75 / 0,14 Мбит/с |
| Голос учителя | Opus 20 мс | 44 кбит/с, непрерывно |
| Голос ученика | Opus 20 мс | 20 кбит/с, говорит 10 % времени, остальное DTX |

Подписки — по правилам режима «Лекция» (по умолчанию в Matís): ученик видит
демонстрацию (верхний слой) и учителя (нижний слой, лента), слышит всех;
учитель видит сетку до 25 учеников (нижний слой). Dynacast включён — неиспользуемые
слои публикатор не шлёт. Запись — кнопкой учителя через API Matís (Room
Composite, шаблон `/egress` приложения); проверено по кадру записи, что
в ней демонстрация и лента с живым видео участников
(`capacity-raw/recording-frame-example.jpg`).

**Качество на клиентах** — по каждому принятому треку: потери по номерам
пакетов, джиттер RFC 3550 (отдельно аудио), перерывы видео > 1 с,
переподключения, обрывы WebSocket, время входа и первого видео.

**Монитор сервера** — раз в 5 с: CPU по ядрам и по контейнерам (cgroup),
частота, температура, счётчики троттлинга, run queue, RAM контейнеров, swap
in/out, диск, трафик и UDP-ошибки ядра, метрики LiveKit и egress.

**Ступень** — 10 минут, в анализ — без первых 90 с (вход участников);
уроки стартуют последовательно (≈200 входов/мин).

**Ограничения методики — важно:**
* Генераторы работали **на этом же сервере** (второй машины нет) — на CPU
  0,6,3,9, вне ядер LiveKit и записи. Их CPU измерен (0,4–0,9) и вычтен.
* Весь медиатрафик шёл через loopback, **мимо сетевой карты**. Сетевая
  вместимость — **расчётная** (трафик, измеренный на клиентах, / 1 Гбит/с);
  реальная полоса провайдера не измерялась (публичные iperf3 недоступны).
* Синтетические клиенты не декодируют видео и не имеют браузерных
  особенностей; TURN-relay под нагрузкой не проверялся (все шли напрямую).

Рекомендуемая рабочая вместимость (с запасом):
* **все уроки записываются** — 2 урока × 30 учеников = **62 пользователя,
  2 записи**. Чтобы запас по CPU записи был ≤ 70 % — записывать 720p15
  (настройка школы «Частота кадров записи»): 65 % против 76 %.
* **запись выборочная** — до **4 уроков × 30 = 124 пользователя** постоянно
  (≈70 % от подтверждённых 6 уроков; LiveKit 34 %, сервер 31 %), из них
  записываются ≤ 2.

Размеры урока 10 и 20 учеников отдельно не мерились. Расчётно LiveKit и
трафик растут примерно пропорционально числу участников (лекция ≈ 2,6 Мбит/с
на участника вниз, ≈ 0,010 CPU LiveKit на участника), а цена записи от
размера класса почти не зависит (лента в записи показывает ~5 камер):
**при записи каждого урока предел — те же 2 урока независимо от размера
класса**.

## 7. Узкие места

1. **Запись (egress)** — первой упирается во всех сценариях с записью:
   1,5–1,7 CPU на запись при 30 fps; при двух записях на одном физическом
   ядре цена растёт (SMT). 15 fps экономит лишь ~15 % — основную работу
   делает Chrome (рендер страницы урока и декодирование видео), а не
   кодирование H.264.
2. **LiveKit** — 0,32 CPU на урок из 31 человека (лекция). Расчётно 70 % его
   4 CPU ≈ 8–9 уроков. Джиттер аудио p95 рос: 7 → 21,7 → 24,4 мс при 2/4/6
   уроках (порог 30) — вероятно, вторым ограничением станет он.
3. **Сеть 1 Гбит/с** — ≈80 Мбит/с исходящего на урок в лекции; 70 % порта ≈
   8–9 уроков (расчёт). В «Обсуждении» трафик выше (не мерился).
4. Приложение, PostgreSQL, Redis, Caddy — < 0,03 CPU каждый, не ограничивают.

## 8. Тротлинг

* Thermal/power throttling: счётчики `thermal_throttle` = 0 во всех ступенях,
  частота держалась 4,27–4,30 ГГц, пик 65 °C (порог 82 °C).
* CFS-троттлинг контейнеров (квоты cgroup): 0.
* Перегрузка вычислений: ядра egress при 2 записях 76–86 %, при 3 на 6 ядрах
  85–91 % — это перегрузка по нашим критериям, хотя кадры не терялись.
* Перегрузка сети/очередей: UDP receive/send buffer errors = 0, drops = 0.
* Ограничение: сетевая карта под тестом не нагружалась (loopback).

## 9. Качество связи

* Потери пакетов на клиентах: 0 во всех ступенях.
* Джиттер аудио p95: 6–29 мс (растёт с нагрузкой, см. п. 7).
* Восстановление при смене сети — по живому уроку пользователя (телефон,
  Wi-Fi → мобильный → слабый Wi-Fi): 4 смены сети, каждая восстановлена
  автоматически за 2,2–2,9 с, без выпадения из урока, без TURN.
* TURN: все пути проверены (UDP 3478, UDP 443, TLS 5349, TLS 443) —
  выделение relay на публичном адресе, relay к чужим адресам запрещён
  (G-10). Под нагрузкой relay не проверялся.

## 10. Запись

* До теста egress принимал **одну** запись на сервер (cpus 3 / cost 3):
  вторая получала 502 «Сервис записи не ответил». Исправлено: cpus 4 /
  cost 1.5 — **две** (проверено без потерь кадров, файлы 30 fps).
* Найден и исправлен баг: вебхуки LiveKit и страница записи упирались в
  лимит 100 запросов/мин на IP (все идут с адреса шлюза Docker) — записи
  зависали в «starting», терялись события посещаемости (коммит 5916d70).
* Все записи после исправления — `ready`, воспроизводимы (ffprobe: H.264
  1280×720, 30 fps, 3 Мбит/с, AAC), запуск 0,05–2,7 с.
* Запуск третьей записи egress отклоняет мгновенно (502) — урок продолжается,
  но без записи, учителю показывается ошибка; повторной попытки нет.

## 11. Риски и непроверенные сценарии

* Профиль B («Обсуждение», учитель + 9 видимых учеников у каждого) — не
  проверен; трафик и CPU LiveKit там выше.
* Профиль C (ограниченная полоса, задержка, потери, обрывы у части клиентов)
  — скрипт подготовлен (`/root/loadtest/profile_c.sh`), не запускался;
  есть только живой урок пользователя (см. п. 9).
* Длительный прогон 60 мин — не проводился: утечки памяти и рост очередей
  со временем не проверены.
* Массовый вход: гостевой вход ограничен 300/мин на один IP — школа за одним
  NAT не впустит больше 300 учеников в минуту.
* Сетевая карта и полоса провайдера под нагрузкой не измерены.
* Только синтетические клиенты; реальные браузеры (декодирование, CPU
  учеников) и TURN-relay под нагрузкой — не проверены.
* Запись, у которой потерялся вебхук, навсегда остаётся «processing» — в
  приложении нет сверки статусов с LiveKit (`ListEgress`).

## 12. Рекомендации

1. **Записывать 720p15**, если допустимо по качеству (настройка школы): −15 %
   CPU на запись, загрузка egress при 2 записях укладывается в 70 %.
2. **Очередь и повтор старта записи** в приложении вместо мгновенной ошибки
   502 при занятом egress; **сверка статусов** записей с LiveKit по таймеру.
3. **Для 3 записей на этом сервере** — отдать egress третье физическое ядро
   (перенести app/PostgreSQL/Redis/Caddy на ядро 0,6: им нужно < 0,1 CPU).
   Измерено: 3 записи на 6 CPU — без потерь, но egress 85 % и джиттер аудио
   28,8 мс. Выигрыш — +1 запись ценой запаса.
4. **Путь к 50 одновременным записям** (расчётные оценки, не измерено):
   * *Room Composite на отдельных машинах* (как сейчас, но egress не на
     сервере уроков): ~1,6 CPU и ~1,75 ГБ на запись → 50 записей ≈ 80
     потоков CPU и ~90 ГБ RAM, например 3–4 сервера по 32 потока / 64 ГБ.
     Egress масштабируется горизонтально через тот же Redis — архитектура
     это поддерживает (`docker-compose.egress.yml`).
   * *Track Egress* (запись треков без перекодирования: демонстрация, камера
     учителя, звук) — почти не нагружает CPU, упирается в диск (~4 Мбит/с на
     урок → 50 уроков ≈ 26 МБ/с записи). Склейка в один ролик — отложенной
     задачей ночью или плеер с синхронными дорожками. Меняет продукт
     (раздельные дорожки вместо готового ролика) — решение за владельцем.
     Утилита для замера подготовлена (`/root/loadtest/eprobe`), не запускалась.
   * *Track Composite* (звук + одно видео, без Chrome) — промежуточный вариант.
5. **Сеть**: при росте выше ~8 уроков без записи — канал > 1 Гбит/с или
   второй сервер LiveKit.
